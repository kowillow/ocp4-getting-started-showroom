[#services]
== 배경 지식: Service

=== Service는 왜 필요한가

**Pod**는 언제든 다시 시작되거나 새로 만들어질 수 있고, 그때마다 새로운 IP 주소를 받습니다. 그래서 다른 무언가가 특정 Pod의 IP 주소를 직접 기억해서 사용한다면, 그 Pod가 재시작되는 순간 연결이 끊어져 버립니다. **Service**는 이 문제를 해결하기 위한 안정적인 창구입니다. Service는 OpenShift 내부에서 트래픽을 **Pod**로 라우팅하는 추상화 계층을 제공하며, 또한 해당 **Pod**로 전송되는 트래픽에 대한 로드 밸런서 역할도 합니다.

예를 들어 증가하는 트래픽을 처리하기 위해 더 많은 ``parksmap`` 인스턴스가 필요하다면,
**Pod**를 더 늘릴 수 있습니다. OpenShift는 이러한 Pod들을 자동으로
**Service**의 엔드포인트로 매핑하며, 들어오는 요청 입장에서는 ``parksmap``이 요청을
더 잘 처리하게 되었다는 것 외에는 별다른 차이를 느끼지 못합니다.

앞서 **컨테이너 이미지** 배포 방식으로 ``parksmap``을 배포했을 때, 이 방식은 Deployment뿐 아니라 **Service**도 함께 자동으로
생성해 주었습니다(``oc new-app`` 같은 CLI 명령이나 **Git에서 가져오기** 같은 다른 배포 방식들도 마찬가지로 Service를 자동 생성합니다). Service는 클러스터 내부에서만 유효한 가상 IP(ClusterIP)를 가지는 내부 구성 요소라는 점을 기억하세요. 그래서 "외부
세계"나 OpenShift 환경 바깥에 있는 것들은 이 IP로 Service에 접근할 수 없습니다. 괜찮습니다. 이 문제를 해결하기 위해 잠시 후 **Route**를 사용하는 방법을 배우게 됩니다.

=== Service는 Pod를 어떻게 찾는가

**Service**는 **Selector**를 사용하여 여러 **Pod**와 매핑됩니다. **Selector**는 **Labels**(Pod에 붙이는 ``app=parksmap``과 같은 key=value 형태의 태그)를 기준으로 어떤 Pod가 트래픽을 받아야 하는지 결정합니다. 즉 Pod가 몇 개이든, 어떤 이름으로 생성되든 상관없이 정해진 Label만 붙어 있으면 그 Service의 트래픽 대상이 됩니다.

직접 YAML 형식으로 작성하는 방법을 포함하여
link:{ocp4_starter_openshift_docs}/html/networking_overview[Service^]에 대한 더 많은 정보는, OpenShift 공식 문서에서 확인할 수 있습니다.

이제 **Service**가 무엇인지 기본 개념을 이해했으니, 방금 배포한 이미지에 대해 생성된
**Service**를 살펴보겠습니다. 여러분의 **Project**에 정의된 **Service**를 확인하려면 다음 명령을 입력합니다:

[source,bash,role="copypaste"]
----
oc get services
----

다음과 유사한 출력이 표시됩니다:

[.console-output]
[source]
----
NAME       TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)    AGE
parksmap   ClusterIP   172.30.22.209   <none>        8080/TCP   15m
----

위 출력에서, ``parksmap``이라는 이름의 **Service**가
172.30.22.209라는 IP에 8080/TCP 포트로 연결되어 있는 것을 확인할 수 있습니다. 각
**Service**는 생성 시 고유한 IP 주소를 받기 때문에 여러분의 IP 주소는 다를 수 있습니다. **Service**의
IP는 고정되며 해당 **Service**가 존재하는 동안 절대 변경되지 않습니다.

**Topology** 화면에서는 ``parksmap`` Deployment를 클릭한 후 **Resources**를 클릭하면 Service 정보를 확인할 수 있습니다.

[.bordershadow]
image::parksmap-serviceslist.png[Resources 탭에서 확인한 parksmap Service 연결 정보,link=self,window=blank]

다음 명령을 사용하여 YAML 형식으로 데이터를 표시함으로써
**Service**에 대한 더 자세한 정보를 확인할 수도 있습니다:

[source,bash,role="copypaste"]
----
oc get service parksmap -o yaml
----

다음과 유사한 출력이 표시됩니다:

[.console-output]
[source]
----
apiVersion: v1
kind: Service
metadata:
  annotations:
    openshift.io/generated-by: OpenShiftWebConsole
  creationTimestamp: "2020-09-30T14:10:12Z"
  labels:
    app: workshop
    app.kubernetes.io/component: parksmap
    app.kubernetes.io/instance: parksmap
    app.kubernetes.io/part-of: workshop
    component: parksmap
    role: frontend
  name: parksmap
  namespace: workshop
  resourceVersion: "1062269"
  selfLink: /api/v1/namespaces/workshop/services/parksmap
  uid: e1ff69c8-cb2f-11e9-82a1-0267eec7e1a0
spec:
  clusterIP: 172.30.22.209
  ports:
  - name: 8080-tcp
    port: 8080
    protocol: TCP
    targetPort: 8080
  selector:
    app: parksmap
    deployment: parksmap
  sessionAffinity: None
  type: ClusterIP
status:
  loadBalancer: {}
----

``selector`` 필드를 주목하고 기억해 두세요. 잠시 후 ``parksmap`` Pod의 Label과 실제로 일치하는지 직접 비교해 보겠습니다.

또는 이전 화면에서 **Service**를 클릭하여 웹 콘솔로 정보를 확인할 수도 있습니다.

[.bordershadow]
image::parksmap-service.png[웹 콘솔에서 확인한 parksmap Service 상세 정보 화면,link=self,window=blank]

``parksmap`` **Pod**의 YAML을 확인하여 **Service**
가 **Selector**를 어떻게 사용하는지 이해해 보세요. 다음 명령을 실행하여 Pod 정보를 확인합니다:

[source,bash,role="copypaste"]
----
oc describe pods
----

``Labels`` 섹션 아래에서 다음을 확인할 수 있습니다:

[.console-output]
[source]
----
app=parksmap
deployment=parksmap
----

이 **Pod** 레이블은 **Service**의 **Selector**가 대상으로 하는 레이블과 일치합니다.

NOTE: **Labels**는 단순한 key-value 쌍입니다. 동일한 **Project**(**Namespace**라고도 함) 내에서 **Selector**와
일치하는 레이블을 가진 모든 **Pod**는 해당 **Service**와 연결됩니다. 이를 직접 확인하려면 다음
명령을 실행하세요:

[source,bash,role="copypaste"]
----
oc describe service parksmap
----

다음과 유사한 출력이 표시됩니다:

[.console-output]
[source,text]
----
Name:              parksmap
Namespace:         workshop
Labels:            app=workshop
                   app.kubernetes.io/component=parksmap
                   app.kubernetes.io/instance=parksmap
                   app.kubernetes.io/part-of=workshop
                   component=parksmap
                   role=frontend
Annotations:       openshift.io/generated-by: OpenShiftWebConsole
Selector:          app=parksmap,deployment=parksmap
Type:              ClusterIP
IP:                172.30.22.209
Port:              8080-tcp  8080/TCP
TargetPort:        8080/TCP
Endpoints:         10.128.2.90:8080
Session Affinity:  None
Events:            <none>
----

왜 엔드포인트가 하나만 나열되는지 궁금할 수 있습니다. 이는 현재 실행 중인
**Pod**가 하나뿐이기 때문입니다. 다음 실습에서는 애플리케이션을 스케일링하는 방법을 배우게 되며,
그 시점에는 **Service**에 연결된 여러 엔드포인트를
확인할 수 있습니다.

== Route

[#routes]
=== 배경 지식: Route

**Service**는 OpenShift 환경 내부에서 추상화와 로드 밸런싱을 제공하지만,
때로는 OpenShift **외부**의 클라이언트(사용자, 시스템, 디바이스 등)가
애플리케이션에 접근해야 하는 경우가 있습니다. 외부 클라이언트는 **Route** 오브젝트로 구성할 수 있는
OpenShift 라우팅 계층을 통해 OpenShift에서 실행 중인 애플리케이션에 접근합니다.

기본 OpenShift 라우터(https://www.haproxy.org/[HAProxy^])는 들어오는
요청의 HTTP 헤더를 사용하여 연결을 어디로 프록시할지 결정합니다. 선택적으로 **Route**에
TLS 같은 보안 설정을 정의할 수 있습니다. **Service**, 그리고 나아가
**Pod**를 외부 세계에서 접근 가능하게 하려면 **Route**를
생성해야 합니다.

[#route_vs_ingress]
=== 배경 지식: OpenShift Route와 Kubernetes Ingress

Kubernetes를 먼저 접해봤다면 **Route** 대신 **Ingress**라는 이름이 익숙할 수 있습니다. 둘은 같은 문제(외부 트래픽을 클러스터 내부 **Service**로 전달하는 것)를 해결하지만, 등장한 배경과 기능 범위가 다릅니다.

**Route**는 OpenShift가 Kubernetes보다 먼저 갖추고 있던 네이티브 오브젝트입니다. Kubernetes 커뮤니티는 이후 벤더 중립적인 표준으로 **Ingress**를 도입했습니다.

오늘날 OpenShift는 두 가지를 모두 지원하며, 클러스터 내부의 OpenShift Router가 **Ingress** 오브젝트를 자동으로 감지해 **Route**로 동기화해 줍니다. 즉 **Ingress**를 만들어도 동작하지만, **Route**가 제공하는 몇 가지 기능은 **Ingress** API만으로는 표현할 수 없습니다.

[cols="1,2,2",options="header"]
|===
|항목 |OpenShift Route |Kubernetes Ingress

|표준 여부
|OpenShift 전용(비표준)
|Kubernetes 표준(모든 배포판에서 동작)

|TLS(Transport Layer Security) Termination 옵션
|Edge, Passthrough, Re-encrypt를 세밀하게 선택 가능
|TLS 활성화 여부만 지정, 세부 termination 방식은 Ingress Controller 구현에 따라 다름

|트래픽 분산(카나리, 블루/그린)
|여러 Route를 동일 호스트에 연결하고 ``weight``로 비율 조정 가능
|Ingress Controller가 어노테이션으로 지원하는 경우에만 가능(표준 API에는 없음)

|생성 방법
|``oc expose``, ``oc create route``, 웹 콘솔에서 바로 생성
|``Ingress`` 오브젝트 작성 + 클러스터에 Ingress Controller 필요(OpenShift는 기본 내장)
|===

이 워크샵에서는 OpenShift 네이티브 기능인 **Route**를 사용합니다. 다른 Kubernetes 배포판으로 옮겨야 하는 애플리케이션이라면 **Ingress**를 선택해 이식성을 높일 수 있습니다.

[#creating_a_route]
=== 실습: Route 생성하기

``parksmap`` 애플리케이션을 배포할 때 **Route**를 생성하는 체크박스를 해제했던 것을
기억하실 겁니다. 원래는 자동으로 생성되었을 것입니다. 다행히 **Route**를 생성하는 것은
간단한 과정입니다.

Route는 OpenShift 콘솔에서 생성하거나 ``oc`` CLI를 사용하여 생성할 수 있습니다. 아래 옵션 중 원하는 방식을 선택하여 route를 추가하세요.

====
**옵션 A: OpenShift 콘솔:**

. **Networking -> Routes**를 클릭한 후 **Create Route** 버튼을 클릭합니다.
. **Name** 필드에 **parksmap**을 입력합니다.
. **Service** 필드에서 **parksmap**을 선택합니다. **Target Port**는 **8080**을 선택합니다.
. **Security** 섹션에서 **Secure route**를 체크합니다. **TLS Termination** 목록에서 **Edge**를 선택합니다.
. 나머지 필드는 비워두고 **Create**를 클릭합니다:
+
image::parksmap-route-create-1.png[Name/Service/TLS Termination 등을 입력하는 Route 생성 화면,link=self,window=blank]

TIP: 클러스터 Apps 도메인에 대한 TLS 인증서가 기본적으로 사용되므로 별도의 인증서를 추가할 필요가 없습니다. OpenShift 클러스터로 연결되는 커스텀 도메인을 사용하고 싶다면 route별로 인증서를 추가할 수 있습니다.

**Route**를 생성할 때 호스트 이름, **Route**의 경로 또는 추가 TLS 설정 같은 다른 옵션도 지정할 수 있습니다.

**옵션 B: ``oc`` 명령줄:**

**Service**를 ``expose``하려면 먼저 기존에 생성된 **Route**가 없는지 확인합니다:

[source,bash,role="copypaste"]
----
oc get routes
----

[.console-output]
[source]
----
No resources found.
----

이제 노출할 **Service** 이름을 확인해야 합니다:

[source,bash,role="copypaste"]
----
oc get services
----

[.console-output]
[source]
----
NAME       CLUSTER-IP      EXTERNAL-IP   PORT(S)    AGE
parksmap   172.30.22.209   <none>        8080/TCP   5h
----

**Service** 이름을 알고 나면 **Route**를 생성하는 것은 간단한 명령 한 번으로 끝나는 작업입니다:

[source,bash,role="copypaste"]
----
oc create route edge parksmap --service=parksmap
----

[.console-output]
[source]
----
route.route.openshift.io/parksmap created
----

====

다음 명령으로 **Route**가 생성되었는지 확인합니다:

[source,bash,role="copypaste"]
----
oc get route
----

[.console-output]
[source,subs="attributes"]
----
NAME       HOST/PORT                                                           PATH   SERVICES   PORT       TERMINATION   WILDCARD
parksmap   parksmap-{ocp4_starter_project}.{ocp4_starter_apps_domain}          parksmap   8080-tcp   edge          None
----

``parksmap`` Deployment의 **Topology** 화면에서 **Resources** 탭 아래로도 **Route**를 확인할 수 있습니다. Topology에서 ``parksmap`` 노드에 화살표 아이콘이 생긴 것을 확인하세요. 이를 클릭하면 브라우저에서 **Route**의 URL이 열립니다.

[.bordershadow]
image::parksmap-route-created.png[생성된 Route로 연결되는 화살표 아이콘이 표시된 Topology 화면,link=self,window=blank]

이제 Topology에서 표시된 URL에서 애플리케이션을 사용할 수 있습니다. 링크를 클릭하면 확인할 수 있습니다.

NOTE: 이 페이지를 처음 여는 경우, 브라우저가 위치 정보 접근 권한을 요청할 수 있습니다. 이는 프런트엔드 앱이 세계 지도를 여러분의 위치로 중앙 정렬하기 위해 필요합니다. 허용하지 않으면 앱은 기본 위치를 사용합니다.

[.bordershadow]
image::parksmap-route-empty-map.png[Route URL로 접속한 parksmap 애플리케이션의 빈 지도 화면,link=self,window=blank]
