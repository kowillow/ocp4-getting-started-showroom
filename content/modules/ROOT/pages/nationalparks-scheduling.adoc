= Pod가 어디에서 실행될지 결정하기: Affinity와 Toleration
:navtitle: Pod가 어디에서 실행될지 결정하기: Affinity와 Toleration

include::vars.adoc[]

지금까지 ``nationalparks``와 MongoDB 등 여러 Pod를 배포했습니다. 그런데 이 Pod들은 실제로 클러스터의 **어느 노드**에서 실행되고 있을까요? 이번 섹션에서는 스케줄러가 Pod를 노드에 배치하는 원리와, 이를 제어하는 몇 가지 방법을 알아봅니다.

WARNING: 이 실습 환경의 클러스터는 **여러 학습자가 함께 사용하는 공유 클러스터**입니다. ``oc adm taint``, ``oc label node``, ``oc adm cordon``처럼 노드 자체를 변경하는 명령은 다른 학습자의 워크로드에 영향을 줄 수 있으므로 이 모듈에서는 사용하지 않습니다. 이 실습은 (1) 노드를 읽기 전용으로 조회하는 것과, (2) 자신의 namespace 안에 있는 Pod의 배치 규칙만 변경하는 것으로 제한합니다.

[#node_scheduling_group]
== 노드와 스케줄링 개념

[#node_scheduling_concepts]
=== 배경 지식: 노드, nodeSelector, Affinity

**Node**는 Pod가 실제로 실행되는 물리 서버 또는 가상 머신입니다. 스케줄러는 다음과 같은 정보를 바탕으로 어떤 노드에 Pod를 배치할지 결정합니다:

* **Label**: 모든 노드는 ``kubernetes.io/hostname``(노드 이름), ``kubernetes.io/os``(운영체제) 같은 라벨을 기본으로 가지고 있고, 관리자가 커스텀 라벨을 추가할 수도 있습니다.
* **nodeSelector**: Pod spec에 ``nodeSelector: {label: value}``를 지정하면, 해당 라벨을 가진 노드에만 스케줄링됩니다. 조건에 맞는 노드가 없으면 Pod는 ``Pending`` 상태로 남습니다.
* **Node Affinity**: nodeSelector보다 더 유연한 규칙(예: "가능하면 이런 노드를 선호하지만, 없으면 다른 곳도 괜찮다")을 표현할 수 있습니다.
* **Pod Affinity/Anti-Affinity**: 특정 노드가 아니라 **다른 Pod와의 관계**를 기준으로 배치합니다. 예를 들어 "같은 앱의 Pod들은 서로 다른 노드에 분산시켜라"처럼 지정할 수 있습니다.
* **Taint와 Toleration**: 관리자가 노드에 "이 노드는 특별한 워크로드만 받는다"는 표시(taint)를 남기고, 그 워크로드의 Pod에는 이를 허용하는 표시(toleration)를 붙이는 방식입니다. 예를 들어 GPU나 고사양 메모리를 가진 노드를 해당 워크로드 전용으로 예약하거나, 반대로 특정 용도로 예약된 노드에 일반 워크로드가 들어오지 못하게 막을 때 사용합니다.

네 가지 방식은 모두 "Pod를 어디에 배치할지"를 다루지만, 무엇을 기준으로 판단하는지와 그 방향이 서로 다릅니다:

[cols="1,2,2,2",options="header"]
|===
|항목 |판단 기준 |동작 방향 |강제 여부

|nodeSelector
|노드에 붙은 라벨
|Pod가 조건에 맞는 노드를 찾아감
|강제 (조건에 맞는 노드가 없으면 ``Pending``)

|Node Affinity
|노드에 붙은 라벨
|Pod가 조건에 맞는 노드를 찾아감
|강제 또는 선호 중 선택 가능

|Pod Affinity/Anti-Affinity
|다른 Pod의 존재 여부(노드 라벨이 아님)
|Pod가 다른 Pod와의 관계를 기준으로 배치됨
|강제 또는 선호 중 선택 가능

|Taint와 Toleration
|노드에 관리자가 남긴 taint 표시
|노드가 기본적으로 Pod를 거부하고, toleration이 있는 Pod만 예외적으로 허용
|taint의 effect(``NoSchedule`` 등) 설정에 따라 다름
|===

NOTE: nodeSelector/Node Affinity와 Taint/Toleration은 방향이 반대입니다. nodeSelector는 "Pod가 원하는 노드를 골라가는" 방식이고, Taint/Toleration은 "노드가 원치 않는 Pod를 걸러내는" 방식입니다. Pod Affinity/Anti-Affinity는 아예 노드가 아니라 다른 Pod를 기준으로 판단한다는 점에서 나머지 셋과 축 자체가 다릅니다.

[#exploring_nodes]
=== 실습: 노드 살펴보기

NOTE: Node는 네임스페이스에 속하지 않는 클러스터 범위 리소스라, 일반 사용자 권한으로는 기본적으로 조회할 수 없습니다. 이 실습이 가능하도록 클러스터 관리자가 여러분의 계정에 Node 조회 권한을 미리 부여해 두었습니다.

먼저 클러스터의 노드 목록을 읽기 전용으로 조회해 봅니다. 아래 명령은 어떤 노드도 변경하지 않습니다.

[source,bash,role="copypaste"]
----
oc get nodes
----

각 노드가 가진 라벨을 확인합니다:

[source,bash,role="copypaste"]
----
oc get nodes --show-labels
----

worker 노드 중 하나를 골라 자세한 정보를 확인합니다:

[source,bash,role="copypaste"]
----
WORKER=$(oc get nodes -l node-role.kubernetes.io/worker -o jsonpath='{.items[0].metadata.name}')
oc describe node $WORKER
----

``Capacity``/``Allocatable`` 항목에서 이 노드의 전체 CPU/메모리와, 스케줄링 가능한 양을 확인할 수 있습니다.

[#pod_anti_affinity]
=== 실습: Pod Anti-Affinity로 분산 배치하기

``nationalparks`` Deployment에 Pod Anti-Affinity 규칙을 추가해, 같은 앱의 Pod들이 서로 다른 노드에 분산되도록 만들어 보겠습니다. 이 규칙은 자신의 namespace 안에서만 동작하며 노드 자체는 변경하지 않습니다.

Pod 스펙(``spec.template.spec``)에 다음과 같은 ``affinity`` 블록을 추가할 것입니다:

[source,yaml]
----
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: nationalparks
        topologyKey: kubernetes.io/hostname
----

NOTE: ``requiredDuringSchedulingIgnoredDuringExecution``(필수, hard)를 사용했습니다. 이는 "반드시 지켜라"는 의미로, 조건을 만족하는 노드가 없으면 Pod는 스케줄링되지 않고 ``Pending`` 상태로 남습니다. 이 클러스터는 노드가 충분하므로 안전하게 사용할 수 있습니다. 노드가 부족한 환경이라면 대신 ``preferredDuringSchedulingIgnoredDuringExecution``(선호, soft)를 사용해 "가능하면 지켜라"는 완화된 조건으로 바꿀 수도 있습니다.

CLI로 바로 적용합니다:

[source,bash,role="copypaste"]
----
oc patch deployment nationalparks --type='json' -p='[{"op":"add","path":"/spec/template/spec/affinity","value":{"podAntiAffinity":{"requiredDuringSchedulingIgnoredDuringExecution":[{"labelSelector":{"matchLabels":{"app":"nationalparks"}},"topologyKey":"kubernetes.io/hostname"}]}}}]'
----

2개로 스케일링해 실제로 다른 노드에 배치되는지 확인합니다:

[source,bash,role="copypaste"]
----
oc scale deployment/nationalparks --replicas=2
oc get pods -l app=nationalparks -o wide
----

[.console-output]
[source]
----
NAME                             READY   STATUS    RESTARTS   AGE   IP            NODE
nationalparks-789c6bc4f4-4x8kq   1/1     Running   0          30s   10.128.2.55   worker-1
nationalparks-789c6bc4f4-9p2wr   1/1     Running   0          10s   10.131.0.62   worker-2
----

``NODE`` 열을 보면 두 Pod가 서로 다른 노드에 배치된 것을 확인할 수 있습니다. 실습이 끝나면 replica를 1로 되돌립니다:

[source,bash,role="copypaste"]
----
oc scale deployment/nationalparks --replicas=1
----

[#tolerations]
=== 실습: Toleration으로 Taint가 걸린 노드에 배치하기

이번에는 Taint가 걸린 노드에 Pod를 배치하려면 Toleration이 왜 필요한지 직접 확인합니다. Taint는 노드 단위로 적용되는 클러스터 전역 설정이라, 학습자가 직접 만들면 같은 클러스터를 쓰는 다른 학습자의 실습에도 영향을 줄 수 있습니다. 그래서 이 실습에 필요한 Taint는 클러스터 관리자가 노드 하나에 미리 설정해 두었습니다.

먼저 어떤 노드에 Taint가 걸려 있는지 찾습니다:

[source,bash,role="copypaste"]
----
oc get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints --no-headers | grep workshop-demo
----

찾은 노드 이름을 변수에 저장합니다:

[source,bash,role="copypaste"]
----
TAINTED_NODE=$(oc get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints --no-headers | grep workshop-demo | awk '{print $1}')
echo $TAINTED_NODE
----

먼저 Toleration 없이, ``nodeSelector``로 이 노드를 콕 집어서 배치하도록 시도합니다:

[source,bash,role="copypaste"]
----
oc patch deployment nationalparks --type='json' -p="[{\"op\":\"add\",\"path\":\"/spec/template/spec/nodeSelector\",\"value\":{\"kubernetes.io/hostname\":\"$TAINTED_NODE\"}}]"
----

Pod 상태를 확인합니다:

[source,bash,role="copypaste"]
----
oc get pods -l app=nationalparks
----

[.console-output]
[source]
----
NAME                             READY   STATUS    RESTARTS   AGE
nationalparks-6b9d8f7c5d-k2x9p   0/1     Pending   0          15s
----

원인을 확인합니다:

[source,bash,role="copypaste"]
----
oc describe pod -l app=nationalparks | grep -A 3 Events:
----

[.console-output]
[source]
----
Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  10s   default-scheduler  0/3 nodes are available: 1 node(s) had untolerated taint {workshop-demo: scheduling}, 2 node(s) didn't match Pod's node affinity/selector.
----

``nodeSelector``는 이 노드를 정확히 지목하고 있지만, Pod에 이 노드의 Taint를 견딜(tolerate) Toleration이 없어서 스케줄러가 배치를 거부합니다. 이제 Toleration을 추가합니다:

[source,bash,role="copypaste"]
----
oc patch deployment nationalparks --type='json' -p='[{"op":"add","path":"/spec/template/spec/tolerations","value":[{"key":"workshop-demo","operator":"Equal","value":"scheduling","effect":"NoSchedule"}]}]'
----

Pod 상태를 다시 확인합니다:

[source,bash,role="copypaste"]
----
oc get pods -l app=nationalparks -o wide
----

[.console-output]
[source]
----
NAME                             READY   STATUS    RESTARTS   AGE   IP            NODE
nationalparks-7d8c6b5f9d-m4k2p   1/1     Running   0          10s   10.129.2.14   worker-1
----

Toleration을 추가하니 같은 노드에 정상적으로 스케줄링된 것을 확인할 수 있습니다. ``nodeSelector``와 ``tolerations``를 원래대로 되돌립니다:

[source,bash,role="copypaste"]
----
oc patch deployment nationalparks --type='json' -p='[{"op":"remove","path":"/spec/template/spec/nodeSelector"},{"op":"remove","path":"/spec/template/spec/tolerations"}]'
----

[source,bash,role="copypaste"]
----
oc get pods -l app=nationalparks
----

Pod가 다시 ``Running`` 상태로 스케줄링되는 것을 확인하며 실습을 마칩니다.
