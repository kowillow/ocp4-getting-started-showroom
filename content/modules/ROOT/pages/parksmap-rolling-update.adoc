= Rolling Update와 Rollback
:navtitle: Rolling Update와 Rollback

include::vars.adoc[]

지금까지 ``parksmap`` Deployment의 Pod 개수를 조절하는 방법을 배웠습니다. 이번에는 애플리케이션 **자체를 안전하게 업데이트**하는 방법을 배웁니다. 서비스 중단 없이 새 버전을 배포하고, 문제가 생기면 즉시 이전 버전으로 되돌리는 것이 목표입니다.

[#rolling_update_strategy]
== 배경 지식: RollingUpdate 전략

**Deployment**는 기본적으로 **RollingUpdate** 전략을 사용합니다. Pod template(컨테이너 이미지, 환경 변수 등)이 변경되면 Deployment는 기존 Pod를 한 번에 모두 교체하지 않습니다. 대신:

. 새로운 Pod template을 가진 새 **ReplicaSet**을 만듭니다.
. 새 ReplicaSet의 Pod를 조금씩 늘립니다.
. 새 Pod가 준비(Ready)되면 기존 ReplicaSet의 Pod를 조금씩 줄입니다.

이 과정은 ``maxSurge``(한 번에 몇 개까지 초과로 띄울 수 있는지)와 ``maxUnavailable``(한 번에 몇 개까지 사용 불가 상태를 허용할지) 두 값으로 세밀하게 제어할 수 있습니다.

앞서 ``parksmap-scaling.adoc``에서 살펴본 Deployment/ReplicaSet 관계를 그대로 활용하는 개념입니다. 다만 이번에는 레플리카 **개수**가 아니라 Pod **내용물**이 바뀝니다.

[#trigger_rolling_update]
== 실습: Pod Template 변경으로 Rolling Update 트리거하기

이미지 태그를 바꾸지 않아도, Pod template이 바뀌기만 하면 rolling update가 시작됩니다. 환경 변수 하나를 추가해 새 ReplicaSet이 생성되는 것을 관찰해 보겠습니다.

현재 이미지를 확인합니다:

[source,bash,role="copypaste"]
----
oc get deployment parksmap -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
----

환경 변수를 추가해 새 롤아웃을 트리거합니다:

[source,bash,role="copypaste"]
----
oc set env deployment/parksmap APP_VERSION=v2
----

롤아웃 진행 상황을 실시간으로 확인합니다:

[source,bash,role="copypaste"]
----
oc rollout status deployment/parksmap
----

[.console-output]
[source]
----
Waiting for deployment "parksmap" rollout to finish: 1 old replicas are pending termination...
deployment "parksmap" successfully rolled out
----

**ReplicaSet** 목록을 다시 확인해 보세요:

[source,bash,role="copypaste"]
----
oc get rs -l app=parksmap
----

[.console-output]
[source]
----
NAME                  DESIRED   CURRENT   READY   AGE
parksmap-65c4f8b676   0         0         0       30m
parksmap-79d5c9f8a2   1         1         1       20s
----

이전 ReplicaSet은 ``DESIRED``/``CURRENT``가 모두 0으로 남아 있습니다. 삭제된 것이 아니라, 나중에 rollback할 때 사용할 수 있도록 기록만 유지되는 것입니다. 롤아웃 히스토리도 확인해 보세요:

[source,bash,role="copypaste"]
----
oc rollout history deployment/parksmap
----

[#failed_update_and_rollback]
== 실습: 실패하는 업데이트와 Rollback

이번에는 존재하지 않는 이미지 태그로 업데이트를 시도해, 배포가 실패했을 때 OpenShift가 어떻게 서비스를 보호하는지 확인합니다.

[source,bash,role="copypaste"]
----
oc set image deployment/parksmap parksmap=quay.io/openshiftroadshow/parksmap:this-tag-does-not-exist
----

Pod 상태를 확인합니다:

[source,bash,role="copypaste"]
----
oc get pods -l app=parksmap
----

[.console-output]
[source]
----
NAME                        READY   STATUS             RESTARTS   AGE
parksmap-79d5c9f8a2-k5gkk   1/1     Running            0          5m
parksmap-8f7b6d4c9-p2x91    0/1     ImagePullBackOff   0          20s
----

새 Pod는 ``ImagePullBackOff`` 상태에 머물러 있지만, 기존 Pod는 여전히 ``Running`` 상태로 서비스를 계속 처리하고 있습니다. RollingUpdate 전략 덕분에 **새 Pod가 준비되기 전까지 기존 Pod를 종료하지 않기 때문**입니다. 이것이 사용자 입장에서 다운타임이 없는 이유입니다.

``oc describe pod``로 원인을 직접 확인할 수도 있습니다:

[source,bash,role="copypaste"]
----
oc describe pod -l app=parksmap | grep -A 5 Events:
----

이제 문제가 있는 롤아웃을 되돌립니다:

[source,bash,role="copypaste"]
----
oc rollout undo deployment/parksmap
----

[.console-output]
[source]
----
deployment.apps/parksmap rolled back
----

정상 상태로 복구되었는지 확인합니다:

[source,bash,role="copypaste"]
----
oc rollout status deployment/parksmap
oc get pods -l app=parksmap
----

마지막으로 히스토리를 다시 확인해 보세요. revision 번호가 하나 더 늘어난 것을 볼 수 있습니다. rollback도 새로운 롤아웃으로 기록되기 때문입니다:

[source,bash,role="copypaste"]
----
oc rollout history deployment/parksmap
----

TIP: 특정 revision으로 돌아가고 싶다면 ``oc rollout undo deployment/parksmap --to-revision=<번호>``처럼 번호를 지정할 수 있습니다.
