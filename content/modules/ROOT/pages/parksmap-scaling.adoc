[#deployments_and_replicasets]
== 배경 지식: Deployment와 ReplicaSet

**Pod**는 스스로를 지키지 않습니다. Pod 하나가 죽거나 실수로 삭제되면, 그 자리를 대신 채워줄 존재가 없는 한 애플리케이션은 그대로 사라진 채로 남습니다.

이 문제를 해결해 주는 것이 **ReplicaSet**(RS)입니다. ReplicaSet은 "정해진 개수의 Pod가 항상 실행되고 있는지" 계속 감시하는 감독관 같은 역할을 합니다. 예를 들어 애플리케이션 서버가 항상 3개의 **Pod**(인스턴스)를 실행하도록 지정해 두면, 그중 하나가 죽거나 삭제되더라도 ReplicaSet이 즉시 새 Pod를 하나 더 만들어 항상 3개를 유지합니다. 이렇게 사람이 개입하지 않아도 스스로 원래 상태를 복구하는 것을 자가 치유(self-healing)라고 부릅니다.

link:{ocp4_starter_openshift_docs}/html/building_applications/deployments[Deployment 문서^]에 따르면 다음과 같습니다:

[quote]
__
ReplicaSet은 지정된 개수의 Pod 레플리카가 항상 실행되도록 보장하는 네이티브 Kubernetes API 오브젝트입니다.
__

그렇다면 **Deployment**는 무엇일까요? Deployment는 ReplicaSet보다 한 단계 위에서 동작합니다. Deployment는 Pod를 직접 관리하지 않고, 대신 ReplicaSet을 관리합니다. 즉 여러분이 "이 이미지를 몇 개의 복제본으로, 어떤 방식으로 업데이트하며 배포하고 싶다"고 Deployment에 정의해 두면, Deployment가 그에 맞는 ReplicaSet을 만들고, 그 ReplicaSet이 실제 Pod 개수를 유지하는 두 단계 구조입니다.

거의 모든 경우에 **Pod**, **Service**, **ReplicaSet**, **Deployment** 리소스를 함께 사용하게 됩니다. 웹 콘솔이나 CLI로 컨테이너 이미지를 배포하면 OpenShift가 이 모든 것을 대신 생성해 줍니다.

[#exploring_deployment_related_objects]
== 실습: Deployment 관련 오브젝트 살펴보기

**ReplicaSet**과 **Deployment**의 배경 지식을 알았으니, 이제 이들이 어떻게 함께 작동하는지 살펴보겠습니다. OpenShift에 ``parksmap`` 이미지를 배포하도록 지시했을 때 생성된 **Deployment**를 확인해 보세요:

[source,bash,role="copypaste"]
----
oc get deployment
----

[.console-output]
[source]
----
NAME       READY   UP-TO-DATE   AVAILABLE   AGE
parksmap   1/1     1            1           20m
----

더 자세한 내용을 확인하려면 **ReplicaSet**(RS)을 살펴봅니다:

[source,bash,role="copypaste"]
----
oc get rs
----

[.console-output]
[source]
----
NAME                  DESIRED   CURRENT   READY   AGE
parksmap-65c4f8b676   1         1         1       21m
----

이 출력은 현재 하나의 **Pod**가 배포되기를 기대하고 있고(``Desired``), 실제로 하나의 **Pod**가 배포되어 있음을(``Current``) 보여줍니다. 원하는 개수를 변경하면 OpenShift에 더 많거나 더 적은 **Pod**를 원한다고 알릴 수 있습니다.

TIP: OpenShift의 **HorizontalPodAutoscaler(HPA)**는 여러 Pod의 CPU 및 메모리 사용량을 모니터링하고, 더 많은 인스턴스를 추가하여 애플리케이션 안정성을 보장하도록 Deployment를 자동으로 업데이트할 수 있습니다. link:{ocp4_starter_openshift_docs}/html/nodes/working-with-pods#nodes-pods-autoscaling[문서에서 Horizontal Pod Autoscaler에 대해^] 더 자세히 알아볼 수 있습니다.

[#scaling_the_application]
== 실습: 애플리케이션 스케일링하기

이 실습에서는 parksmap 애플리케이션을 2개의 인스턴스로 스케일링합니다. ``oc scale`` 명령을 사용하거나 OpenShift 웹 콘솔에서 Desired Count를 늘려서 수행할 수 있습니다. 원하는 방법을 선택하세요.

[source,bash,role="copypaste"]
----
oc scale --replicas=2 deployment/parksmap
----

또는 **Developer Perspective**에서 Pod를 2개로 스케일링할 수도 있습니다. Topology 화면에서 ``parksmap`` Deployment를 클릭하고 **Details** 탭을 선택합니다:

[.bordershadow]
image::parksmap-details.png[parksmap Deployment의 Details 탭에 표시된 Pod 시각화 화면,link="self",window=_blank]

다음으로, Pod 시각화 옆의 **^** 아이콘을 클릭하여 Pod를 2개로 스케일링합니다.

[.bordershadow]
image::parksmap-scaleup.png[Pod 개수를 2개로 늘리는 스케일 업 조작 화면,link="self",window=_blank]

레플리카 개수가 변경되었는지 확인하려면 다음 명령을 실행합니다:

[source,bash,role="copypaste"]
----
oc get rs
----

[.console-output]
[source]
----
NAME                  DESIRED   CURRENT   READY   AGE
parksmap-65c4f8b676   2         2         2       23m
----

이제 레플리카가 2개인 것을 확인할 수 있습니다. ``oc get pods`` 명령으로 Pod 개수를 확인해 보세요:

[source,bash,role="copypaste"]
----
oc get pods
----

[.console-output]
[source]
----
NAME                        READY   STATUS    RESTARTS   AGE
parksmap-65c4f8b676-fxcrq   1/1     Running   0          92s
parksmap-65c4f8b676-k5gkk   1/1     Running   0          24m
----

마지막으로, **Service**가 두 개의 엔드포인트를 정확히 반영하고 있는지 확인합니다:

[source,bash,role="copypaste"]
----
oc describe svc parksmap
----

다음과 유사한 출력이 표시됩니다. **Service**가 이제 두 개의 **Endpoint**를 대상으로 하고 있음을 확인하세요:

[.console-output]
[source]
----
Name:              parksmap
Namespace:         wksp-user1
Labels:            app=workshop
                   app.kubernetes.io/component=parksmap
                   app.kubernetes.io/instance=parksmap
                   app.kubernetes.io/part-of=workshop
                   component=parksmap
                   role=frontend
Annotations:       openshift.io/generated-by: OpenShiftWebConsole
Selector:          app=parksmap,deployment=parksmap
Type:              ClusterIP
IP:                172.30.22.209
Port:              8080-tcp  8080/TCP
TargetPort:        8080/TCP
Endpoints:         10.128.2.90:8080,10.131.0.40:8080
Session Affinity:  None
Events:            <none>
----

**Service**의 엔드포인트를 확인하는 또 다른 방법은 다음과 같습니다:

[source,bash,role="copypaste"]
----
oc get endpoints parksmap
----

다음과 유사한 출력이 표시됩니다:

[.console-output]
[source]
----
NAME       ENDPOINTS                           AGE
parksmap   10.128.2.90:8080,10.131.0.40:8080   45m
----

각 Pod는 OpenShift 환경 내에서 고유한 IP를 받기 때문에 여러분의 IP 주소는 다를 수 있습니다. 엔드포인트 목록을 보면 하나의 **Service** 뒤에 몇 개의 **Pod**가 있는지 빠르게 확인할 수 있습니다.

Developer Perspective에서도 두 **Pod**가 모두 실행 중인 것을 확인할 수 있습니다:

[.bordershadow]
image::parksmap-scaled.png[Developer Perspective에서 확인한 실행 중인 Pod 2개 현황,link="self",window=_blank]

전반적으로, 애플리케이션을 스케일링하는 것은 이렇게 간단합니다. OpenShift는 기존 이미지의 새 인스턴스를 실행하는 것이므로 애플리케이션 스케일링은 매우 빠르게 이루어질 수 있으며, 특히 새 Pod가 https://kubernetes.io/docs/concepts/scheduling-eviction/kube-scheduler/[스케줄링된^] 노드에 이미지가 캐시되어 있다면 더욱 그렇습니다.

[#application_self_healing]
== 실습: 애플리케이션 자가 치유(Self Healing) 확인하기

OpenShift의 **RS**는 원하는 개수의 **Pod**가 실행되고 있는지 지속적으로 모니터링하기 때문에, 원하는 레플리카 개수와 현재 개수가 일치하지 않을 경우 OpenShift가 상황을 "고칠" 것이라고 예상할 수 있습니다.

현재 두 개의 **Pod**가 실행 중이므로, "실수로" 하나를 죽이면 어떤 일이 일어나는지 확인해 볼 수 있습니다. ``oc get pods`` 명령을 다시 실행하고 **Pod** 이름 하나를 선택합니다. 그런 다음 다음을 수행합니다:

[source,bash,role="copypaste"]
----
oc delete pod parksmap-7dfd599cd7-vgc7z && oc get pods
----

[.console-output]
[source]
----
pod "parksmap-65c4f8b676-k5gkk" deleted
NAME                        READY   STATUS            RESTARTS     AGE
parksmap-65c4f8b676-bjz5g   1/1     ContainerCreating   0          9s
parksmap-65c4f8b676-fxcrq   1/1     Running             0          4m48s
----

무언가 눈치채셨나요? 하나의 컨테이너가 삭제되었지만, 이미 그 자리에 새로운 컨테이너가 생성되고 있습니다.

방금 확인한 자가 치유는 **RS가 Pod의 개수만 확인**하는 방식입니다. Pod가 존재하는지만 보고, 그 안의 애플리케이션이 실제로 정상 동작하는지는 신경 쓰지 않습니다. OpenShift는 여기서 한 단계 더 나아가, 애플리케이션 인스턴스의 liveness 및/또는 readiness를 확인하는 별도의 기능도 제공합니다. 기본 확인만으로 충분하지 않은 경우, OpenShift는 확인을 수행하기 위해 컨테이너 내부에서 명령을 실행할 수도 있게 해줍니다. 이 명령은 설치된 어떤 언어로든 작성된 스크립트일 수 있습니다.

이러한 health check를 사용하면, Pod 자체는 멀쩡히 떠 있어도 그 안의 ``parksmap`` 애플리케이션이 정상 상태가 아니라고 OpenShift가 판단할 경우 해당 인스턴스를 삭제하고 그 자리에 새 인스턴스를 생성해, 항상 원하는 개수의 "정상" 레플리카가 유지되도록 할 수 있습니다.

애플리케이션 프로빙(probing)에 대한 더 자세한 내용은 문서의
link:{ocp4_starter_openshift_docs}/html/building_applications/application-health[Application Health^]
섹션과 이 가이드의 뒷부분에서 확인할 수 있습니다.

[#scale_down]
== 실습: 스케일 다운

계속 진행하기 전에, 애플리케이션을 다시 인스턴스 1개로 스케일 다운하세요. 원하는
방법을 자유롭게 사용하면 됩니다.

WARNING: Pod를 1개로 스케일 다운하지 않으면 이후 섹션에서 예기치 않은 동작이 발생할 수 있습니다. 이는 애플리케이션이 코딩된 방식 때문이며 OpenShift와는 관련이 없습니다.
