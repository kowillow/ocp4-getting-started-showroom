= 리소스 관리와 쿼터
:navtitle: 리소스 관리와 쿼터

include::vars.adoc[]

각 Project는 리소스 쿼터나 제한 같은 제약 조건을 가질 수 있습니다. 지금까지는 ``parksmap``을 자유롭게 스케일링했지만, 실제 클러스터는 유한한 자원입니다. 이번 섹션에서는 컨테이너 하나가 사용할 수 있는 자원을 제한하는 방법과, 프로젝트 전체가 사용할 수 있는 총량을 제한하는 방법을 배웁니다.

[#requests_limits_group]
== Requests와 Limits

[#requests_and_limits]
=== 배경 지식: Requests와 Limits

컨테이너마다 CPU와 메모리에 대해 두 가지 값을 지정할 수 있습니다:

* **Requests**: 스케줄러가 Pod를 배치할 노드를 고를 때 "이 정도는 반드시 확보해 달라"고 보장을 요청하는 값입니다. 요청한 만큼의 자원 여유가 없는 노드에는 Pod가 스케줄링되지 않습니다.
* **Limits**: 컨테이너가 이 값을 초과해 사용하려 하면 CPU는 스로틀링(제한)되고, 메모리는 OOMKilled(Out Of Memory) 상태로 강제 종료됩니다. 즉, 컨테이너가 사용할 수 있는 **최대치**를 의미합니다.

link:{ocp4_starter_openshift_docs}/html/nodes/working-with-pods#nodes-pods-configuring[Requests와 Limits에 대한 문서^]에서 더 자세히 알아볼 수 있습니다.

[#configuring_resources]
=== 실습: Deployment에 Requests/Limits 설정하기

``parksmap`` Deployment에 requests/limits를 설정해 보겠습니다. 먼저 값을 너무 작게 설정하면 어떤 일이 벌어지는지 직접 확인해 봅니다.

[source,bash,role="copypaste"]
----
oc set resources deployment/parksmap --requests=cpu=100m,memory=64Mi --limits=cpu=200m,memory=128Mi
----

Pod 상태를 확인합니다:

[source,bash,role="copypaste"]
----
oc get pods -l app=parksmap
----

다음과 유사한 출력이 표시됩니다:

[.console-output]
[source]
----
NAME                        READY   STATUS             RESTARTS      AGE
parksmap-65c4f8b676-k5gkk   0/1     CrashLoopBackOff   3 (20s ago)   90s
----

원인을 자세히 확인합니다:

[source,bash,role="copypaste"]
----
oc describe pod -l app=parksmap | grep -A 5 "Last State"
----

[.console-output]
[source]
----
Last State:     Terminated
  Reason:       OOMKilled
  Exit Code:    137
----

``Reason: OOMKilled``를 통해 메모리가 부족해 컨테이너가 강제 종료됐음을 확인할 수 있습니다. ``parksmap``은 웹 화면 서빙과 WebSocket(STOMP) 브로커, 백엔드 API Gateway 역할을 한 프로세스 안에서 모두 처리하는 JVM 기반 애플리케이션이라 실제로는 최대 600MiB 안팎까지 메모리를 사용하는데, limit을 128Mi로 너무 작게 잡아서 정상적으로 뜨기도 전에 계속 강제 종료된 것입니다.

이처럼 Requests/Limits는 애플리케이션이 실제로 필요로 하는 자원을 고려해서 설정해야 합니다. 너무 작게 잡으면 애플리케이션이 정상적으로 뜨지 못하고, 너무 크게 잡으면 클러스터 자원을 낭비하게 됩니다. 적절한 값으로 다시 설정합니다:

[source,bash,role="copypaste"]
----
oc set resources deployment/parksmap --requests=cpu=100m,memory=512Mi --limits=cpu=500m,memory=1Gi
----

적용된 값을 확인합니다:

[source,bash,role="copypaste"]
----
oc describe deployment parksmap | grep -A 4 Limits
----

[.console-output]
[source]
----
    Limits:
      cpu:     500m
      memory:  1Gi
    Requests:
      cpu:      100m
      memory:   512Mi
----

Pod가 정상적으로 ``Running`` 상태가 되는지 확인합니다:

[source,bash,role="copypaste"]
----
oc get pods -l app=parksmap
----

다음과 유사한 출력이 표시됩니다:

[.console-output]
[source]
----
NAME                        READY   STATUS    RESTARTS   AGE
parksmap-79d5c9f8a2-x8k2p   1/1     Running   0          30s
----

NOTE: CPU도 너무 낮게 잡으면 스로틀링 때문에 애플리케이션 응답이 느려질 수 있으므로, 여유를 두고 ``500m``(0.5코어)로 설정합니다.

[#resourcequota_group]
== ResourceQuota

[#resource_quota]
=== 배경 지식: ResourceQuota

**Requests**/**Limits**가 Pod 하나에 대한 제약이라면, **ResourceQuota**는 Project(namespace) **전체**에 대한 총량 제약입니다. 여러 팀이 하나의 클러스터를 공유할 때, 한 프로젝트가 자원을 독점하지 못하도록 막는 안전장치입니다. ResourceQuota는 동시에 실행 가능한 **Pod 개수**뿐 아니라, ``requests.cpu``/``requests.memory``/``limits.cpu``/``limits.memory`` 같은 **CPU/메모리 총량**도 함께 제한할 수 있습니다.

다만 CPU/메모리 항목을 ResourceQuota에 포함시키면, 그 순간부터 이 Project에 생성되는 **모든** Pod가 반드시 자체적으로 requests/limits 값을 가지고 있어야 합니다(값을 지정하지 않은 Pod는 **LimitRange**로 기본값을 채워주지 않는 한 생성이 거부됩니다). 이 워크샵 실습 환경에는 이런 복잡함 없이 핵심 개념만 확인할 수 있도록, **Pod 개수**에 대한 ResourceQuota만 미리 설정되어 있습니다.

[#create_resource_quota]
=== 실습: 사전 설정된 ResourceQuota 확인하기

일반 사용자 권한으로는 ResourceQuota를 직접 생성할 수 없고, 웹 콘솔의 **Workloads** 메뉴에도 ResourceQuotas 항목이 없습니다. ResourceQuota는 Project 전체의 자원 한도를 정하는 관리자 영역의 오브젝트이기 때문입니다. 그래서 이번 실습에서는 클러스터 관리자가 여러분의 Project에 미리 설정해 둔 ResourceQuota를 확인하고, 그 한도에 실제로 부딪혀 보겠습니다.

먼저 이 namespace에 이미 적용된 쿼터를 확인합니다:

[source,bash,role="copypaste"]
----
oc get resourcequota
----

[.console-output]
[source]
----
NAME                                AGE     REQUEST   LIMIT
resourcequota/workshop-quota        1d                        pods: 0/12
----

적용된 쿼터의 세부 내용을 확인합니다:

[source,bash,role="copypaste"]
----
oc describe resourcequota workshop-quota
----

NOTE: 이 ResourceQuota는 **Pod 개수**만 제한합니다. CPU/메모리 총량까지 제한하려면 앞서 설명한 것처럼 LimitRange를 함께 구성해야 하지만, 이 워크샵에서는 핵심 개념(namespace 전체에 대한 총량 제약)만 확인하기 위해 Pod 개수만 사용합니다.

[#quota_in_action]
=== 실습: 쿼터 한도에서 스케일링해보기

이제 ``pods: "12"`` 한도에 부딪힐 때까지 ``parksmap``을 스케일링해 보겠습니다. 지금까지는 ``parksmap``만 배포했으므로, 이 Project에는 아직 ``parksmap`` Pod 1개만 실행 중입니다.

[source,bash,role="copypaste"]
----
oc scale --replicas=12 deployment/parksmap
----

Pod와 ReplicaSet 상태를 확인합니다:

[source,bash,role="copypaste"]
----
oc get rs -l app=parksmap
oc get events --field-selector reason=FailedCreate
----

[.console-output]
[source]
----
LAST SEEN   TYPE      REASON        OBJECT                        MESSAGE
10s         Warning   FailedCreate  replicaset/parksmap-79d5c9f8a2   Error creating: pods "parksmap-79d5c9f8a2-x8k2p" is forbidden: exceeded quota: workshop-quota, requested: pods=1, used: pods=12, limited: pods=12
----

``exceeded quota`` 메시지를 통해 ResourceQuota가 실제로 새 Pod 생성을 막고 있음을 확인할 수 있습니다. **ReplicaSet**은 요청받은 개수(``DESIRED``)를 계속 유지하려고 시도하지만, 쿼터 때문에 실제로는(``CURRENT``) 그보다 적은 Pod만 만들어집니다.

계속 진행하기 전에, ``parksmap``을 다시 인스턴스 1개로 스케일 다운하세요:

[source,bash,role="copypaste"]
----
oc scale --replicas=1 deployment/parksmap
----

WARNING: Pod를 1개로 스케일 다운하지 않으면 이후 섹션에서 예기치 않은 동작이 발생할 수 있습니다.
