= Redis 캐시와 StatefulSet
:navtitle: Redis 캐시와 StatefulSet

include::vars.adoc[]

지금까지 MongoDB는 Deployment로 잘 동작했습니다. 하지만 매번 데이터베이스를 조회하는 대신, 자주 조회되는 응답을 캐시하면 ``nationalparks`` API가 더 빨라질 수 있습니다. 이런 캐시 계층에는 흔히 Redis 같은 인메모리 데이터 저장소를 사용합니다. 이번 섹션에서는 Redis를 **StatefulSet**으로 배포해 봅니다.

NOTE: MongoDB는 Deployment로도 이 워크숍의 목적에는 충분합니다. 다만 Pod의 신원(identity)과 저장 공간이 유지되어야 하는 워크로드(캐시, 데이터베이스 등)에는 일반적으로 Deployment 대신 StatefulSet이 더 적합합니다. 이 모듈에서는 그 차이를 Redis를 통해 직접 확인합니다. 사실 MongoDB는 지금 영구 저장소 없이 임시(ephemeral) 상태로 동작하고 있어 StatefulSet으로 전환하는 것도 좋은 후속 과제가 될 수 있지만, 이미 구성해 둔 MongoDB 설정을 건드리지 않기 위해 이 모듈에서는 Redis로 동일한 StatefulSet 동작 방식을 보여줍니다.

[#statefulsets]
== 배경 지식: StatefulSet과 PersistentVolume

**Deployment**가 관리하는 Pod는 서로 완전히 동일하고 교체 가능하다고 가정합니다. 어떤 Pod가 죽어도 새 Pod가 대신 그 자리를 채우면 그만입니다. 하지만 일부 워크로드는 다음과 같은 특성이 필요합니다:

* **안정적인 네트워크 식별자**: Pod 이름이 ``redis-0``, ``redis-1``처럼 예측 가능하고 재시작 후에도 유지됩니다.
* **순서 있는 배포/스케일링**: Pod가 0번부터 순서대로 생성되고, 스케일 다운 시에는 역순으로 종료됩니다.
* **영구 저장소**: 각 Pod가 자신만의 ``PersistentVolumeClaim``(PVC)을 가지며, Pod가 재시작되어도 같은 볼륨에 다시 연결됩니다.

**StatefulSet**의 ``volumeClaimTemplates`` 필드는 Pod마다 독립된 PVC를 자동으로 생성해 줍니다. Deployment에서는 지원하지 않는 기능입니다. 여기서 **PersistentVolume**(PV)은 클러스터에 실제로 존재하는 저장소 자원이고, PVC는 Pod가 그 저장소를 사용하겠다고 요청하는 수단이라는 점을 구분해 두면 이해하기 쉽습니다. 클러스터에 동적 프로비저닝 스토리지가 설정되어 있다면(``common-environment.adoc``에서 확인한 내용입니다), ``storageClassName``을 지정하지 않아도 PVC가 자동으로 바인딩됩니다.

[#deploy_redis_statefulset]
== 실습: Redis를 StatefulSet으로 배포하기

StatefulSet은 Pod에 안정적인 네트워크 이름을 부여하기 위해 **Headless Service**(ClusterIP가 없는 Service)가 필요합니다. 먼저 Service를 만듭니다. **Networking** → **Services**에서 **Create Service** → **From YAML**을 선택합니다:

[source,yaml,role="copypaste",subs="attributes"]
----
apiVersion: v1
kind: Service
metadata:
  name: redis
  namespace: {ocp4_starter_project}
spec:
  clusterIP: None
  selector:
    app: redis
  ports:
    - port: 6379
      targetPort: 6379
----

**Create**를 클릭합니다. 이제 **Workloads** → **StatefulSets**에서 **Create** → **From YAML**을 선택하고 다음 YAML을 붙여넣습니다:

[source,yaml,role="copypaste",subs="attributes"]
----
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: redis
  namespace: {ocp4_starter_project}
spec:
  serviceName: redis
  replicas: 1
  selector:
    matchLabels:
      app: redis
  template:
    metadata:
      labels:
        app: redis
        component: nationalparks
        role: cache
    spec:
      containers:
        - name: redis
          image: registry.redhat.io/rhel9/redis-7:latest
          ports:
            - containerPort: 6379
          volumeMounts:
            - name: redis-data
              mountPath: /var/lib/redis/data
  volumeClaimTemplates:
    - metadata:
        name: redis-data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 1Gi
----

[#verifying_persistence]
== 실습: 영속성 검증하기

``parksmap-scaling.adoc``에서 Pod를 강제로 삭제했을 때 새 Pod가 즉시 대신 생성되는 "자가 치유"를 확인했습니다. 이번에는 한 걸음 더 나아가, **데이터도 함께** 살아남는지 확인해 보겠습니다.

먼저 Redis에 값을 하나 저장합니다:

[source,bash,role="copypaste"]
----
oc rsh redis-0 redis-cli SET greeting "hello from redis-0"
----

[.console-output]
[source]
----
OK
----

값이 저장되었는지 확인합니다:

[source,bash,role="copypaste"]
----
oc rsh redis-0 redis-cli GET greeting
----

이제 Pod를 강제로 삭제합니다:

[source,bash,role="copypaste"]
----
oc delete pod redis-0
oc get pods -l app=redis
----

[.console-output]
[source]
----
pod "redis-0" deleted
NAME      READY   STATUS    RESTARTS   AGE
redis-0   1/1     Running   0          8s
----

같은 이름 ``redis-0``으로 새 Pod가 다시 생성되었습니다. 저장했던 값이 남아있는지 확인합니다:

[source,bash,role="copypaste"]
----
oc rsh redis-0 redis-cli GET greeting
----

[.console-output]
[source]
----
"hello from redis-0"
----

이번에는 데이터가 사라지지 않았습니다. StatefulSet이 관리하는 PVC는 Pod가 삭제되고 재생성되어도 그대로 다시 연결되기 때문입니다.
