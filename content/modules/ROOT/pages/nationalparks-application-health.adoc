[#readiness_and_liveness_probes]
== 배경 지식: Readiness Probe와 Liveness Probe
애플리케이션이 "실행 중"인 것과 "요청을 처리할 준비가 된 것"은 다른 이야기입니다. 예를 들어 컨테이너 프로세스 자체는 멀쩡히 떠 있어도, 내부적으로 멈춰버렸거나(deadlock) 아직 초기화가 끝나지 않아 요청을 제대로 처리하지 못하는 상태일 수 있습니다. OpenShift는 이 두 가지 상황을 각각 확인하기 위해 애플리케이션 상태 확인이라는 기능을 제공하며, 여기에는 두 가지 종류가 있습니다:

* Readiness probe
* Liveness probe

문서의
link:{ocp4_starter_openshift_docs}/html/building_applications/application-health[Application
Health^] 섹션에는 다음과 같이 정의되어 있습니다:

[glossary]
Liveness Probe::
  Liveness probe는 해당 프로브가 설정된 컨테이너가 여전히
  실행 중인지 확인합니다. Liveness probe가 실패하면 ``kubelet``(각 노드에서 컨테이너를 실제로 실행하고 관리하는 에이전트)이 컨테이너를 종료하며,
  이후 재시작 정책의 적용을 받습니다. Pod 설정의
  ``spec.containers[].livenessProbe`` 항목을 설정하여 liveness check를 지정합니다.
Readiness Probe::
  Readiness probe는 컨테이너가 요청을 처리할 준비가 되었는지 판단합니다. 만약
  readiness probe가 실패하면, OpenShift는 해당 컨테이너의 IP 주소를 Service의
  엔드포인트 목록에서 제거해, 컨테이너가 실행 중이더라도 준비되기 전까지는 트래픽을 받지 않도록 합니다.
  Pod 설정의 ``spec.containers[].readinessProbe`` 항목을 설정하여 readiness check를 지정합니다.

복잡하게 들리지만 실제로는 그렇지 않습니다. 웹 콘솔을 사용하여
``nationalparks`` 애플리케이션에 이러한 probe를 추가해 보겠습니다.

[#add_health_checks]
== 실습: 상태 확인(Health Check) 추가하기
실제와 유사한 CI/CD 파이프라인을 구현할 것이므로, 애플리케이션의 "개발" 버전에
대해 몇 가지 테스트를 진행하게 됩니다. 하지만 앱을 테스트하려면 앱이 준비된
상태여야 합니다. 이때 OpenShift의 애플리케이션 상태 확인 기능이 매우 유용하게 쓰입니다.

기존 ``nationalparks`` 배포에 readiness probe와 liveness probe를 모두
추가해 보겠습니다. 이렇게 하면 OpenShift는 readiness check를 통과할 때까지 어떤
인스턴스도 service에 추가하지 않으며, liveness check에 실패한 비정상 인스턴스는
재시작되도록 보장합니다.

**Topology** 화면에서 ``nationalparks``를 클릭합니다. 사이드 패널에서 **Actions** 드롭다운 메뉴를 클릭하고 **Add Health Checks**를 선택합니다.

[.bordershadow]
image::nationalparks-application-health-menu.png[Actions 드롭다운 메뉴에서 Add Health Checks 선택 화면,link="self",window=_blank]

**Add Readiness Probe**를 클릭하고 **Path** 필드에 다음을 추가합니다:

[source,text,role=copypaste]
----
/ws/healthz/
----

**Port** 8080, **Type** HTTP GET 같은 나머지 기본 설정은 그대로 둡니다. 오른쪽 하단의 작은 회색 체크 표시를 클릭하여 확정합니다:

[.bordershadow]
image::nationalparks-application-health-settings.png[Readiness Probe의 Path/Port/Type 설정 화면,link="self",window=_blank]

Liveness Probe에 대해서도 동일한 과정을 반복합니다. **Add Liveness Probe**를 클릭하고 **Path** 필드에 다음을 추가합니다:

[source,text,role=copypaste]
----
/ws/healthz/
----

**Port** 8080, **Type** HTTP GET 같은 나머지 기본 설정은 그대로 둡니다. 오른쪽 하단의 작은 회색 체크 표시를 클릭하여 확정합니다.

마지막으로 **Add**를 클릭하여 모든 새 변경 사항을 확정합니다:

[.bordershadow]
image::nationalparks-application-health-add.png[Readiness와 Liveness Probe가 추가된 후 Add 버튼을 클릭하는 화면,link="self",window=_blank]


이러한 변경 사항이 새로운 배포를 유발한 것을 확인할 수 있습니다. 설정 변경으로
간주되었기 때문입니다.

[#add_startup_probe]
== 실습: Startup Probe 추가하기

Readiness probe와 liveness probe만으로는 부족한 경우가 있습니다. 시작하는 데 시간이 오래 걸리는 애플리케이션이라면, liveness probe가 애플리케이션이 미처 다 시작하기도 전에 "죽었다"고 판단해 컨테이너를 재시작해 버릴 수 있습니다. 이 문제를 막아주는 것이 **Startup Probe**입니다.

Startup probe가 설정되어 있으면, 다른 모든 probe는 startup probe가 성공할 때까지 비활성화됩니다. 즉, 애플리케이션이 충분히 여유 있게 시작할 시간을 벌어준 다음에야 liveness/readiness probe가 정상적으로 동작하기 시작합니다.

세 가지 probe의 차이를 표로 정리하면 다음과 같습니다:

[cols="1,2,2,2",options="header"]
|===
|항목 |Startup Probe |Readiness Probe |Liveness Probe

|목적
|시작이 느린 애플리케이션에 충분한 준비 시간을 확보해 준다
|지금 이 순간 트래픽을 받을 준비가 되었는지 판단한다
|계속 정상 동작 중인 상태인지 판단한다

|동작 시점
|Pod가 시작될 때 딱 한 번만 통과하면 그 뒤로는 다시 확인하지 않는다
|Pod가 살아있는 동안 계속 반복해서 확인한다
|Pod가 살아있는 동안 계속 반복해서 확인한다

|실패했을 때
|계속 실패하면 컨테이너가 재시작된다(Liveness와 결과가 같음)
|컨테이너는 재시작되지 않고 Service의 트래픽 대상에서만 빠진다
|컨테이너가 재시작된다

|다른 probe와의 관계
|성공하기 전까지는 Readiness/Liveness probe 자체가 동작하지 않는다
|Startup probe가 성공한 뒤부터 독립적으로 동작한다
|Startup probe가 성공한 뒤부터 독립적으로 동작한다
|===

NOTE: 이 실습에서는 세 probe가 모두 같은 경로(``/ws/healthz/``)를 확인합니다. 경로가 같아도 역할은 다릅니다. Startup probe는 이제 막 시작한 애플리케이션이 준비될 때까지 기다려 주는 문지기 역할이고, Readiness probe는 지금 이 순간 트래픽을 보내도 되는지를 계속 감시하는 역할입니다.

**Topology** 화면에서 ``nationalparks``를 클릭합니다. 사이드 패널에서 **Actions** 드롭다운 메뉴를 클릭하고 **Add Health Checks**를 선택합니다.

**Add Startup Probe**를 클릭하고 **Path** 필드에 다음을 추가합니다:

[source,text,role=copypaste]
----
/ws/healthz/
----

**Port** 8080, **Type** HTTP GET은 그대로 두되, **Failure Threshold**를 ``30``, **Period Seconds**를 ``10``처럼 넉넉하게 설정합니다. 이렇게 하면 애플리케이션이 최대 5분(30회 x 10초)까지 시작 시간을 확보할 수 있습니다. 오른쪽 하단의 작은 회색 체크 표시를 클릭하여 확정한 후, **Add**를 클릭해 변경 사항을 저장합니다.

[.bordershadow]
image::nationalparks-application-health-startup-probe.png[Add Startup Probe 설정 화면,link="self",window=_blank]

새 Pod가 뜬 후, ``oc describe pod``로 ``Startup:`` 항목이 새로 추가된 것을 확인합니다:

[source,bash,role="copypaste"]
----
oc describe pod -l app=nationalparks | grep -A 1 Startup:
----

[.console-output]
[source]
----
    Startup:      http-get http://:8080/ws/healthz/ delay=0s timeout=1s period=10s #success=1 #failure=30
----

이제 ``nationalparks``는 readiness, liveness, startup 세 종류의 probe를 모두 갖추게 되었습니다.
