= 환경변수와 ConfigMap
:navtitle: 환경변수와 ConfigMap

include::vars.adoc[]

앞서 ``nationalparks`` 애플리케이션을 배포했지만, 아직 연결할 데이터베이스는 없습니다. 이 애플리케이션은 곧 MongoDB에 연결하게 될 텐데, 그때 필요한 연결 정보(호스트 이름, 데이터베이스 이름)를 지금 미리 준비해 두려고 합니다.

**환경 변수(environment variable)**는 프로세스가 시작될 때 운영체제(컨테이너 환경에서는 컨테이너 런타임)로부터 전달받는 key-value 쌍입니다. 애플리케이션 코드는 이 값을 읽어서 동작을 바꿀 수 있는데, 예를 들어 "어떤 데이터베이스 서버에 연결할지"를 코드에 직접 적어두는 대신 환경 변수로 읽어오게 만들면, 코드를 다시 빌드하지 않고도 배포되는 환경마다 다른 값을 넣어줄 수 있습니다.

문제는 이 환경 변수 **값을 어디서 가져오느냐**입니다. 가장 간단한 방법은 Deployment에 값을 리터럴 문자열로 직접 적어 넣는 것이지만, 민감하지 않은 설정값(호스트 이름, 데이터베이스 이름 등)이라 해도 이렇게 직접 입력하는 것은 좋은 습관이 아닙니다. 값을 바꾸려면 Deployment 자체를 수정해야 하고, 같은 값을 여러 Deployment에서 재사용하기도 어렵습니다. 이번 섹션에서는 이런 값을 **ConfigMap**으로 미리 준비해 두고, Deployment는 그 ConfigMap을 참조하도록 만들어 이 문제를 예방합니다.

[#configmap_group]
== ConfigMap

[#configmaps_vs_secrets]
=== 배경 지식: ConfigMap과 Secret

**ConfigMap**과 **Secret**은 API 상으로 거의 같은 모양을 가진 오브젝트입니다. 이 둘의 공통점은 key-value 쌍의 목록을 저장하고, 환경 변수나 볼륨으로 Pod에 주입할 수 있다는 것입니다.

차이는 딱 하나입니다: **민감한 데이터인가, 아닌가**입니다.

* **ConfigMap**은 데이터베이스 호스트 이름, 기능 플래그, 로그 레벨처럼 유출되어도 큰 문제가 없는 설정값에 사용합니다.
* **Secret**은 비밀번호, 토큰, 인증서처럼 노출되면 안 되는 값에 사용합니다. Secret의 값은 base64로 인코딩되어 저장되지만, 이는 암호화가 아니라 단순 인코딩이라는 점에 유의해야 합니다. 대신 OpenShift는 Secret에 대해 더 제한적인 RBAC(Role-Based Access Control) 접근 제어를 적용할 수 있습니다.

두 오브젝트 모두 애플리케이션 이미지를 다시 빌드하지 않고도 환경별로 다른 값을 주입할 수 있게 해준다는 공통의 목적을 가지고 있습니다. 잠시 후 데이터베이스를 실제로 배포할 때는 자격 증명을 Secret으로 준비하게 되는데, 그전에 먼저 민감하지 않은 연결 정보를 ConfigMap으로 준비해 보겠습니다.

[#create_configmap]
=== 실습: ConfigMap 생성하기

**워크로드(Workloads)** → **구성 맵(ConfigMaps)**에서 오른쪽 상단의 **ConfigMap 만들기(Create Configmap)** 버튼을 클릭하고 **From YAML**을 선택합니다.

[.bordershadow]
image::nationalparks-configmap-create.png[ConfigMap Create From YAML 다이얼로그,link=self,window=blank]

에디터에 다음 YAML을 붙여넣습니다:

[source,yaml,role="copypaste",subs="attributes"]
----
apiVersion: v1
kind: ConfigMap
metadata:
  name: nationalparks-config
  namespace: {ocp4_starter_project}
data:
  MONGODB_SERVER_HOST: mongodb
  MONGODB_DATABASE: parksapp
----

폼 하단의 **Create** 버튼을 클릭합니다.

NOTE: ``MONGODB_SERVER_HOST``의 값 ``mongodb``는 잠시 후 데이터베이스 모듈에서 배포할 MongoDB **Service**의 이름과 미리 맞춰둔 것입니다. 아직 그 Service는 존재하지 않지만, 이름만 미리 정해서 ConfigMap에 담아 두는 것입니다.

[#wire_configmap_env]
=== 실습: ConfigMap 값을 환경 변수로 연결하기

이제 ``nationalparks`` Deployment에 방금 만든 ConfigMap의 값을 환경 변수로 연결합니다. **Topology** 화면에서 ``nationalparks`` Deployment를 클릭하고 __Actions → Edit Deployment__를 선택합니다.

**Environment Variables** 섹션으로 이동해 **+Add from ConfigMap or Secret**을 클릭하고 이름으로 다음을 입력합니다:

[source,text,role=copypaste]
----
MONGODB_SERVER_HOST
----

값으로는 resource로 ``nationalparks-config``를, key로 ``MONGODB_SERVER_HOST``를 선택합니다.

다시 **+Add from ConfigMap or Secret**을 클릭하고 이름으로 다음을 입력합니다:

[source,text,role=copypaste]
----
MONGODB_DATABASE
----

값으로는 resource로 ``nationalparks-config``를, key로 ``MONGODB_DATABASE``를 선택합니다.

[.bordershadow]
image::nationalparks-configmap-env-wire.png[Edit Deployment 대화 상자에서 ConfigMap을 참조하는 환경 변수 추가 화면,link=self,window=blank]

대화 상자 하단의 **Save** 버튼을 클릭합니다. 새 **ReplicaSet**이 롤아웃되는 것을 확인할 수 있습니다:

[source,bash,role="copypaste"]
----
oc get rs -l app=nationalparks
----

지금까지 살펴본 것처럼 ConfigMap 값은 환경 변수 외에 **볼륨**으로도 Pod에 마운트할 수 있습니다. 파일 형태의 설정(예: ``.properties``, ``.conf`` 파일)을 다뤄야 할 때 유용한 방식이며, 방식만 다를 뿐 ConfigMap을 만들고 Deployment에 연결하는 기본 흐름은 지금 실습한 것과 동일합니다.
