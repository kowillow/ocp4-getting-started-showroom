== MongoDB 배포와 연결

[#configmaps_vs_secrets]
=== 배경 지식: 환경 변수, ConfigMap과 Secret

**환경 변수(environment variable)**는 프로세스가 시작될 때 운영체제(컨테이너 환경에서는 컨테이너 런타임)로부터 전달받는 key-value 쌍입니다. 애플리케이션 코드는 이 값을 읽어서 동작을 바꿀 수 있는데, 예를 들어 "어떤 데이터베이스 서버에 연결할지"를 코드에 직접 적어두는 대신 환경 변수로 읽어오게 만들면, 코드를 다시 빌드하지 않고도 배포되는 환경마다 다른 값을 넣어줄 수 있습니다.

문제는 이 환경 변수 **값을 어디서 가져오느냐**입니다. 가장 간단한 방법은 Deployment에 값을 리터럴 문자열로 직접 적어 넣는 것이지만, 민감하지 않은 설정값(호스트 이름, 데이터베이스 이름 등)이라 해도 이렇게 직접 입력하는 것은 좋은 습관이 아닙니다. 값을 바꾸려면 Deployment 자체를 수정해야 하고, 같은 값을 여러 Deployment에서 재사용하기도 어렵습니다. 민감하지 않은 값은 **ConfigMap**으로, 비밀번호 같은 민감한 값은 **Secret**으로 미리 준비해 두고, Deployment는 그 값을 참조하도록 만들어 이 문제를 예방합니다.

**ConfigMap**과 **Secret**은 API 상으로 거의 같은 모양을 가진 오브젝트입니다. 이 둘의 공통점은 key-value 쌍의 목록을 저장하고, 환경 변수나 볼륨으로 Pod에 주입할 수 있다는 것입니다.

차이는 딱 하나입니다: **민감한 데이터인가, 아닌가**입니다.

* **ConfigMap**은 데이터베이스 호스트 이름, 기능 플래그, 로그 레벨처럼 유출되어도 큰 문제가 없는 설정값에 사용합니다.
* **Secret**은 비밀번호, 토큰, 인증서처럼 노출되면 안 되는 값에 사용합니다. Secret의 값은 base64로 인코딩되어 저장되지만, 이는 암호화가 아니라 단순 인코딩이라는 점에 유의해야 합니다. 대신 OpenShift는 Secret에 대해 더 제한적인 RBAC(Role-Based Access Control) 접근 제어를 적용할 수 있습니다.

두 오브젝트 모두 애플리케이션 이미지를 다시 빌드하지 않고도 환경별로 다른 값을 주입할 수 있게 해준다는 공통의 목적을 가지고 있습니다. 먼저 MongoDB를 배포하면서 자격 증명을 **Secret**으로 준비하고, 이어서 nationalparks가 사용할 연결 정보(호스트 이름, 데이터베이스 이름)를 **ConfigMap**으로 준비하겠습니다.

[#storage]
=== 배경 지식: 데이터베이스 연결 설정

유용한 애플리케이션 대부분은 데이터를 어딘가에 저장해야 하는 "상태를 가진(stateful)" 구성 요소가 필요하며, 보통 데이터베이스가 그 역할을 맡습니다. 이 섹션에서는
애플리케이션 아키텍처에 MongoDB를 추가하고, ``nationalparks`` Deployment가 이
데이터베이스에 연결하도록 구성합니다.

MongoDB 자체의 관리자 자격 증명과, ``nationalparks`` 애플리케이션이 사용할 데이터베이스 사용자 자격 증명은 모두 민감한 정보이므로 앞서 살펴본 대로 **Secret**에 담아 관리합니다. 먼저 이 Secret부터 만들고 MongoDB를 배포하겠습니다.

NOTE: Secret을 환경 변수로 전달하면 값이 컨테이너 안에 그대로 노출된다는 한계가 있습니다. 애플리케이션이 오류 발생 시 환경 변수 전체를 로그로 남기는 경우가 흔한데, 이 경우 Secret 값이 로그에 그대로 찍혀버릴 수 있습니다. 그래서 실제 프로덕션 환경에서는 Secret을 환경 변수 대신 **볼륨으로 마운트**해서 앱이 파일로 읽게 하거나(Secret이 변경되면 Pod 재시작 없이도 파일 내용이 자동으로 갱신됩니다), HashiCorp Vault 같은 외부 Secret 관리 도구와 연동하는 경우가 많습니다. 다만 이는 이 워크샵의 범위를 벗어나므로, 개념을 익히는 단계인 여기서는 더 간단한 환경 변수 방식을 사용합니다.

데이터베이스에는 자격 증명 외에도 실제로 저장할 데이터가 필요합니다. 컨테이너의 파일 시스템은 컨테이너가 재시작되면 함께 사라지므로, MongoDB가 다시 시작되어도 데이터가 남아있게 하려면 영구 저장소를 연결해야 합니다. 이 영구 저장소는 세 가지 오브젝트로 이루어집니다:

* **PersistentVolume**(PV): 클러스터에 실제로 존재하는 저장 공간 하나를 나타내는 오브젝트입니다. 클라우드 블록 스토리지나 NFS 같은 실제 스토리지 시스템의 용량을 클러스터가 사용할 수 있도록 등록해 둔 것입니다.
* **StorageClass**: PV를 어떤 방식으로 만들지 정의해 둔 일종의 설계도입니다. 클러스터 관리자가 미리 여러 StorageClass를 만들어 두면, 사용자는 그중 하나를 골라 요청하기만 하면 됩니다.
* **PersistentVolumeClaim**(PVC): Pod가 "이 정도 용량과 접근 방식의 저장 공간이 필요합니다"라고 요청하는 오브젝트입니다.

PVC를 만들 때 StorageClass를 지정하면(또는 클러스터의 기본 StorageClass가 자동으로 적용되면), 클러스터가 그 설계도에 따라 PV를 자동으로 만들어 PVC와 연결해 줍니다. 이를 동적 프로비저닝(dynamic provisioning)이라고 하며, 대부분의 경우 PV를 직접 만들 필요 없이 PVC만 요청하면 충분합니다. 이 섹션에서는 Secret과 PVC를 함께 준비해 MongoDB를 배포합니다.

[#create_mongodb_instance]
=== 실습: MongoDB 배포하기

첫 번째 단계는 데이터베이스 연결 자격 증명 같은 민감한 정보를 저장하는 데 사용할 **Secret**을 생성하는 것입니다.
**워크로드(Workloads)** → **시크릿(Secrets)**에서 오른쪽 상단의 **만들기(Create)** 버튼을 클릭하고 **출처: YAMl(From YAML)**을 선택합니다.

[.bordershadow]
image::mongodb_create_secret.png[Secrets 화면에서 Create → From YAML을 선택하는 메뉴,link=self,window=blank]

에디터에 다음 YAML을 붙여넣습니다:

[source,yaml,role="copypaste",subs="attributes"]
----
apiVersion: v1
kind: Secret
metadata:
  name: mongodb-credentials
  namespace: {ocp4_starter_project}
type: Opaque
stringData:
  admin-usr: admin
  admin-pwd: secret
  app-usr: parksapp
  app-pwd: keepsafe
----

[.bordershadow]
image::mongodb_create_secret_dialog.png[mongodb-credentials Secret YAML이 입력된 편집기 화면,link=self,window=blank]

폼 하단의 **Create** 버튼을 클릭합니다.

Secret이 준비되었으니, 이전에 다른 애플리케이션을 추가할 때처럼 오른쪽 상단의 **+** 아이콘을 클릭합니다. **Container images** 옵션을 선택합니다.

Image 섹션의 **Image name from external registry** 필드에 다음을 입력합니다:

[source,text,role=copypaste]
----
mongo:6.0.4
----

**Runtime icon**은 ``mongodb``를 선택합니다.

General 섹션의 **Application**은 ``workshop``으로 둡니다. **Name** 필드에는 다음을 입력합니다:

[source,text,role=copypaste]
----
mongodb
----

[.bordershadow]
image::mongodb_deploy_image_image.png[mongo 컨테이너 이미지와 Runtime 아이콘을 지정하는 Image 섹션,link=self,window=blank]

* 리소스 유형(Resource type) 드롭다운이 **배포(Deployment)** 옵션으로 설정되어 있는지 확인합니다.

* **고급 배포 옵션 표시(how advanced Deployment options)**를 클릭합니다. 여기에서 앞서 생성한 ``mongodb-credentials`` Secret에서 값을 가져오는 두 개의 환경 변수를 추가합니다.

**+Add from ConfigMap or Secret**을 클릭하고 이름으로 다음을 입력합니다:

[source,text,role=copypaste]
----
MONGO_INITDB_ROOT_USERNAME
----

값으로는 resource로 ``mongodb-credentials``를, key로 ``admin-usr``을 선택합니다.

다시 **+Add from ConfigMap or Secret**을 클릭하고 이름으로 다음을 입력합니다:

[source,text,role=copypaste]
----
MONGO_INITDB_ROOT_PASSWORD
----

값으로는 resource로 ``mongodb-credentials``를, key로 ``admin-pwd``를 선택합니다.

* Advanced options:
    - Create a route → 데이터베이스는 OpenShift 클러스터 외부의 클라이언트가 접근하지 않을 것이므로 **체크 해제**합니다.

[.bordershadow]
image::mongodb_deploy_image_general.png[MongoDB 배포의 환경 변수와 Create a route 옵션이 표시된 General 섹션,link=self,window=blank]

페이지 하단의 '이름을 클릭하여 고급 옵션에 액세스합니다(Click on the names to access advanced options for)' 부분에서 **라벨(Labels)**를 클릭하고, 3개를 추가합니다. 텍스트를 복사하여 붙여넣은 후, 키보드의 return 또는 enter를 누르면 입력됩니다.

[.bordershadow]
image::nationalparks-configure-service4.png[Labels 섹션을 펼쳐 레이블을 추가하는 화면,link=self,window=blank]

Application 그룹의 이름입니다:

[source,text,role=copypaste]
----
app=workshop
----

다음은 이 배포의 이름입니다:

[source,text,role=copypaste]
----
component=nationalparks
----

마지막으로, 이 구성 요소가 전체 애플리케이션에서 수행하는 역할입니다:

[source,text,role=copypaste]
----
role=database
----

마지막으로, 페이지 하단의 **Create** 버튼을 클릭하여 MongoDB 컨테이너를 배포합니다.

이 배포 마법사에는 볼륨을 추가하는 항목이 없으므로, 영구 저장소는 배포가 끝난 뒤 별도로 연결합니다. 
일반적으로는 **Topology** 화면에서 구성 요소를 클릭하고 사이드 패널의 **Actions** 드롭다운에서 **Add Storage**를 선택한 뒤, PVC Name/Access Mode/Size/Mount Path만 입력하면 손쉽게 스토리지를 붙일 수 있습니다.

[.bordershadow]
image::mongodb_deploy_image_volume.png[Add Storage 과정에서 경고가 뜨는 화면,link=self,window=blank]

하지만 MongoDB는 예외적인 경우입니다. ``mongo`` 컨테이너 이미지는 자체적으로 ``/data/db``와 ``/data/configdb`` 두 경로를 볼륨으로 선언해 두고 있어서, OpenShift가 Deployment를 생성하는 시점에 이 두 경로에 임시 저장소(``emptyDir``)를 이미 자동으로 마운트해 둔 상태입니다(볼륨이 2개 자동 생성되므로, 그중 어떤 것이 ``/data/db``용인지는 인덱스가 아니라 마운트 경로로 찾아야 합니다). 그래서 Add Storage로 같은 경로(``/data/db``)에 PVC를 추가하려 하면 "이미 사용 중인 경로"라는 경고가 뜨고, 그대로 진행해도 기존 ``emptyDir``이 그대로 남아있어 PVC가 실제로는 연결되지 않습니다.

NOTE: ``/data/configdb``는 MongoDB가 **샤딩된 클러스터의 config server** 역할을 할 때만 사용하는 디렉터리이며, 이 워크샵처럼 단일 mongod 인스턴스(standalone)로 실행할 때는 사용되지 않습니다. 그래서 이 경로는 PVC로 바꾸지 않고 ``emptyDir``로 남겨 둬도, Pod가 재시작될 때 실질적으로 잃을 데이터가 없습니다. 실제 데이터가 저장되는 ``/data/db``만 PVC로 교체하면 충분합니다.

이런 경우에는 CLI로 기존 볼륨을 PVC로 **교체(overwrite)**해야 합니다. 먼저 ``/data/db``에 실제로 마운트되어 있는 볼륨의 이름을 마운트 경로 기준으로 찾습니다:

[source,bash,role="copypaste"]
----
oc get deployment mongodb -o jsonpath='{.spec.template.spec.containers[0].volumeMounts[?(@.mountPath=="/data/db")].name}{"\n"}'
----

그 이름을 그대로 사용해, 같은 이름의 볼륨을 새 PVC로 덮어씁니다:

[source,bash,role="copypaste"]
----
VOL_NAME=$(oc get deployment mongodb -o jsonpath='{.spec.template.spec.containers[0].volumeMounts[?(@.mountPath=="/data/db")].name}')
oc set volume deployment/mongodb --add --overwrite --name=$VOL_NAME -t pvc --claim-name=mongodb-data --claim-size=500Mi --mount-path=/data/db
----

PVC가 정상적으로 생성되고 연결되었는지 확인합니다:

[source,bash,role="copypaste"]
----
oc get pvc mongodb-data
----

``Bound`` 상태라면 정상입니다. 이렇게 하면 MongoDB Pod가 재시작되거나 다시 스케줄링되더라도, PVC에 연결된 저장 공간 덕분에 데이터가 사라지지 않습니다.

다음 단계는 nationalparks 애플리케이션이 연결을 생성하는 데 사용할 특정 사용자를 이 MongoDB 인스턴스에 생성하는 것입니다. 이를 위해 Topology 화면에서 **MongoDB Deployment**를 클릭한 후, 오른쪽 화면에 표시되는 해당 **Pod**를 클릭합니다.

[.bordershadow]
image::mongodb_deployment_topology_pod.png[Topology 화면에서 MongoDB Deployment의 Pod를 선택하는 화면,link=self,window=blank]

Pod 세부 정보 화면으로 이동하며, 여기에서 **Terminal**을 클릭하면 해당 컨테이너에서 터미널 세션을 시작할 수 있습니다.

[.bordershadow]
image::mongodb_pod_details_terminal.png[Pod 세부 정보 화면의 Terminal 탭,link=self,window=blank]

다음 스니펫을 복사하여 터미널 창에 붙여넣어, 올바른 설정과 역할을 가진 데이터베이스 사용자를 생성합니다:

[source,bash,role=copypaste]
----
mongosh -u admin -p secret --authenticationDatabase admin --eval 'use parksapp' --eval 'db.createUser({user: "parksapp", pwd: "keepsafe", roles: [{ role: "dbAdmin", db: "parksapp" },{ role: "readWrite", db: "parksapp" }]})' --quiet
----

WARNING: 이 명령을 실행해야 nationalparks 애플리케이션이 사용할 ``parksapp`` 데이터베이스 사용자가 생성됩니다. 이 단계를 건너뛰면 이후 데이터를 적재하는 과정이 인증 실패로 진행되지 않으므로 반드시 실행해야 합니다.

NOTE: 프로덕션 환경에서는 컨테이너 entrypoint를 수정하거나 https://kubernetes.io/docs/concepts/workloads/pods/init-containers/[init container^]를 사용하여 데이터베이스 설정을 관리할 수 있습니다.

명령이 성공하면 다음과 같은 출력이 표시됩니다:

[.console-output]
[source]
----
{ ok: 1 }
----

[#configmap_group]
== ConfigMap 생성과 환경 변수 연결

MongoDB와 전용 애플리케이션 사용자까지 준비되었으니, 이제 ``nationalparks``가 이 데이터베이스에 연결할 때 사용할 환경 변수를 준비합니다. 민감하지 않은 값(호스트 이름, 데이터베이스 이름)은 **ConfigMap**에 담고, 조금 전 만든 ``mongodb-credentials`` **Secret**의 자격 증명과 함께 ``nationalparks`` Deployment에 한 번에 연결하겠습니다.

[#create_configmap]
=== 실습: ConfigMap 생성하기

**워크로드(Workloads)** → **구성 맵(ConfigMaps)**에서 오른쪽 상단의 **ConfigMap 만들기(Create Configmap)** 버튼을 클릭하고 **From YAML**을 선택합니다.

[.bordershadow]
image::nationalparks-configmap-create.png[ConfigMap Create From YAML 다이얼로그,link=self,window=blank]

에디터에 다음 YAML을 붙여넣습니다:

[source,yaml,role="copypaste",subs="attributes"]
----
apiVersion: v1
kind: ConfigMap
metadata:
  name: nationalparks-config
  namespace: {ocp4_starter_project}
data:
  MONGODB_SERVER_HOST: mongodb
  MONGODB_DATABASE: parksapp
----

폼 하단의 **만들기(Create)** 버튼을 클릭합니다.

NOTE: ``MONGODB_SERVER_HOST``의 값 ``mongodb``는 방금 배포한 MongoDB 컨테이너 이미지가 생성한 MongoDB **Service**의 이름과 정확히 일치합니다.

[#wire_env_vars]
=== 실습: nationalparks Deployment에 환경 변수 연결하기

이제 ``nationalparks`` Deployment에 방금 만든 ConfigMap과, 앞서 MongoDB를 배포할 때 사용한 ``mongodb-credentials`` Secret의 값을 환경 변수로 연결합니다. **Topology** 화면에서 ``nationalparks`` Deployment를 클릭하고 __동작(Actions) → Deployment 편집(Edit Deployment)__를 선택합니다.

[.bordershadow]
image::nationalparks_deployment_edit.png[nationalparks Deployment의 Actions 메뉴에서 Edit Deployment 선택,link=self,window=blank]

**환경 변수(Environment Variables)** 섹션으로 이동해 **+구성 맵 또는 시크릿에서 추가(Add from ConfigMap or Secret)**을 클릭하고 이름으로 다음을 입력합니다:

[source,text,role=copypaste]
----
MONGODB_SERVER_HOST
----

값으로는 resource로 ``nationalparks-config``를, key로 ``MONGODB_SERVER_HOST``를 선택합니다.

다시 **+구성 맵 또는 시크릿에서 추가(Add from ConfigMap or Secret)**을 클릭하고 이름으로 다음을 입력합니다:

[source,text,role=copypaste]
----
MONGODB_DATABASE
----

값으로는 resource로 ``nationalparks-config``를, key로 ``MONGODB_DATABASE``를 선택합니다.

이어서 같은 방법으로 Secret에서 자격 증명 두 개도 추가합니다. **+구성 맵 또는 시크릿에서 추가(Add from ConfigMap or Secret)**을 클릭하고 이름으로 다음을 입력합니다:

[source,text,role=copypaste]
----
MONGODB_USER
----

값으로는 resource로 ``mongodb-credentials``를, key로 ``app-usr``을 선택합니다.

다시 **+구성 맵 또는 시크릿에서 추가(Add from ConfigMap or Secret)**을 클릭하고 이름으로 다음을 입력합니다:

[source,text,role=copypaste]
----
MONGODB_PASSWORD
----

값으로는 resource로 ``mongodb-credentials``를, key로 ``app-pwd``를 선택합니다.

[.bordershadow]
image::nationalparks-env-vars-all.png[Edit Deployment 대화 상자에 ConfigMap과 Secret에서 가져온 환경 변수 4개가 모두 추가된 화면,link=self,window=blank]

대화 상자 하단의 **저장(Save)** 버튼을 클릭합니다. 
그리고 다음 명령어를 실행하면, 새로운 환경변수를 가진 Pod들이 새 **ReplicaSet**으로 롤아웃되는 것을 확인할 수 있습니다.

[source,bash,role="copypaste"]
----
oc get rs -l app=nationalparks
----

[NOTE]
====
``nationalparks``는 이제 ``MONGODB_SERVER_HOST``, ``MONGODB_DATABASE``, ``MONGODB_USER``, ``MONGODB_PASSWORD`` 네 개의 환경 변수를 통해 방금 배포한 MongoDB에 연결됩니다.

OpenShift에 애플리케이션을 배포할 때는, 종속 시스템에 대한 연결 파라미터를 정의할 때
항상 Secret이나 ConfigMap을 사용하여 환경 변수를 생성하는 것이 좋습니다. 이렇게 하면
소스 코드를 수정하지 않고도 다양한 환경에서 애플리케이션을 이식할 수 있습니다. 연결을
수행하고 데이터베이스 스키마를 생성하는 소스 파일은 다음에서 확인할 수
있습니다:

[source,text,subs="attributes"]
----
{ocp4_starter_openshift_roadshow}/nationalparks/blob/master/src/main/java/com/openshift/evg/roadshow/parks/db/MongoDBConnection.java#L44-l48
----

지금은 ConfigMap과 Secret 값을 모두 환경 변수에 삽입했지만, 이 외에 **볼륨**으로도 Pod에 마운트할 수 있습니다. 파일 형태의 설정(예: ``.properties``, ``.conf`` 파일)을 다뤄야 할 때 유용한 방식이며, 방식만 다를 뿐 ConfigMap이나 Secret을 만들고 Deployment에 연결하는 기본 흐름은 지금 실습한 것과 동일합니다.
====

== 데이터 주입 및 프런트엔드 앱 확인

[#data_data_everywhere]
=== 실습: 데이터, 데이터, 어디에나

이제 데이터베이스가 배포되었으니, ``nationalparks`` 웹
서비스를 다시 방문하여 데이터를 조회해 볼 수 있습니다:

[source,text,role="copypaste",subs="attributes"]
----
https://nationalparks-{ocp4_starter_project}.{ocp4_starter_apps_domain}/ws/data/all
----

결과는 어떨까요?

[.console-output]
[source]
----
[]
----

데이터는 어디에 있을까요? 지금까지 진행한 과정을 생각해 보세요. 애플리케이션을
배포한 다음 데이터베이스를 배포했습니다. 하지만 실제로 데이터베이스
**안에** 데이터를 로드한 적은 없습니다.

nationalparks 애플리케이션은 바로 이 작업을 수행하는 엔드포인트도 제공합니다. 웹 브라우저에서 이 URL을 열어 ``nationalparks`` 애플리케이션이 MongoDB에 샘플 데이터셋을 삽입하도록 해보세요:

[source,text,role="copypaste",subs="attributes"]
----
https://nationalparks-{ocp4_starter_project}.{ocp4_starter_apps_domain}/ws/data/load
----

결과는 어떨까요?

[.console-output]
[source]
----
Items inserted in database: 2893
----

이제 다시 ``/ws/data/all``로 이동하면 엄청난 양의 JSON 데이터를 확인할 수 있습니다.

[source,text,role="copypaste",subs="attributes"]
----
https://nationalparks-{ocp4_starter_project}.{ocp4_starter_apps_domain}/ws/data/all
----

NOTE: Firefox 54 같은 일부 브라우저에서는 결과 JSON을 제대로 파싱하지 못해 오류가 보고되는 경우가 있습니다. 이는 브라우저 문제이며 애플리케이션은 정상적으로 동작하고 있습니다.

이제 마지막으로, 프런트엔드 앱인 parksmap URL을 방문하여 브라우저에서 지도를 다시 확인해보세요.

[source,text,role="copypaste",subs="attributes"]
----
https://parksmap-{ocp4_starter_project}.{ocp4_starter_apps_domain}
----

[.bordershadow]
image::nationalparks-databases-new-parks.png[parksmap 지도에 국립공원 마커가 표시된 화면,link=self,window=blank]

이제 공원들이 갑자기 나타나는 것을 확인할 수 있습니다. 정말 멋지네요!
