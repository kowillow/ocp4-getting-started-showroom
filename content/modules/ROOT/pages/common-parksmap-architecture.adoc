= ParksMap 아키텍처
:navtitle: ParksMap 아키텍처

include::vars.adoc[]

이 섹션에서는 이 워크샵 전체에서 사용할 ParksMap 애플리케이션의 아키텍처를 소개합니다. 아키텍처를 이해하면 개발자 관점에서 수행하게 될 작업을 더 잘 이해하는 데 도움이 됩니다.

ParksMap은 **마이크로서비스** 아키텍처로 만들어졌습니다. 하나의 커다란 프로그램이 모든 일을 다 하는 대신, 각자 맡은 역할이 분명한 여러 개의 작은 Service로 나뉘어 있고, 이 Service들은 서로 독립적으로 배포되고 스케일링됩니다. 또한 원본 ParksMap 애플리케이션 모음은 **폴리글랏(polyglot)** 하게 설계되어 있어, 각 Service를 Java, .NET, Node.js 등 서로 다른 언어와 프레임워크로 구현할 수 있습니다. 다만 이 워크샵에서는 혼란을 줄이기 위해 모든 Service를 **Java**로 통일해서 진행합니다.

== 메인 Service: 프런트엔드 지도 애플리케이션

메인 Service는 사용자가 브라우저로 접속하는 웹 애플리케이션입니다. 위 다이어그램에서 ``Parksmap Web`` 박스를 보면 그 안에 ``Web``과 ``API Gateway``라는 두 개의 하위 박스가 있는데, 이 둘이 바로 프런트엔드 애플리케이션을 이루는 두 가지 핵심 구성 요소입니다:

1. **API Gateway**(서버 측 구성 요소): 다이어그램의 ``API Gateway`` 박스에 해당합니다. 현재 클러스터에 어떤 백엔드 Service가 떠 있는지 계속 추적하고 있다가(이 추적 방법은 바로 다음 섹션에서 다룹니다), 브라우저가 ``/ws/data/all`` 같은 경로로 지도 데이터를 요청하면 등록된 각 백엔드에 실제 요청을 대신 보내고 그 결과를 모아서 돌려줍니다. 덕분에 브라우저는 nationalparks나 mlbparks 같은 개별 백엔드의 주소를 전혀 몰라도 되고, 오직 이 API Gateway하고만 대화하면 됩니다.
2. **Web**(클라이언트 측 구성 요소): 다이어그램의 ``Web`` 박스에 해당하며, JavaScript로 만들어져 브라우저에서 실행됩니다. 지도에 지리공간 데이터를 시각화하고, WebSocket으로 API Gateway와 연결을 유지합니다. 새 백엔드가 등록되거나 사라질 때마다 API Gateway가 이 WebSocket 채널로 알림을 보내주기 때문에, 페이지를 새로고침하지 않아도 지도에 마커가 자동으로 나타나거나 사라집니다.

== 백엔드 Service: 실제 지도 데이터를 제공하는 곳

원본 ParksMap 애플리케이션 모음에는 다양한 지도 및 지리공간 정보를 제공하는 독립적인 백엔드 Service들이 있습니다:

* 전 세계 국립공원(National Parks) 정보를 제공하는 **nationalparks** Service
* 북미 메이저리그 야구 경기장(MLB Stadiums) 정보를 제공하는 **mlbparks** Service

이 워크샵에서는 이 중 **nationalparks** 하나만 직접 배포하고 실습합니다. mlbparks는 원본 애플리케이션 모음에 존재하는 백엔드이지만, 이번 워크샵의 실습 범위에는 포함되지 않습니다.

== 백엔드는 어떻게 서로를 찾을까요?

앞서 살펴본 API Gateway가 사용 가능한 모든 백엔드에 대한 통신 창구 역할을 하는데, 이때 어떤 백엔드가 존재하는지는 소스 코드에 하드코딩되어 있지 않습니다. 대신 OpenShift가 제공하는 서비스 디스커버리(service discovery) 메커니즘을 사용해, 특정 Label이 붙은 Route를 클러스터에서 동적으로 검색합니다. 즉 nationalparks Service에 올바른 Label을 붙이는 순간, ParksMap이 이를 자동으로 발견해서 지도에 표시해 줍니다. 이 Label을 실제로 붙이는 방법은 뒤에 나올 실습에서 직접 다룹니다.
