= ParksMap 아키텍처
:navtitle: ParksMap 아키텍처

include::vars.adoc[]

이 섹션에서는 이 워크숍 전체에서 사용할 ParksMap 애플리케이션의 아키텍처를 소개합니다. 아키텍처를 이해하면 개발자 관점에서 수행하게 될 작업을 더 잘 이해하는 데 도움이 됩니다.

ParksMap은 **마이크로서비스** 아키텍처로 만들어졌습니다. 하나의 커다란 프로그램이 모든 일을 다 하는 대신, 각자 맡은 역할이 분명한 여러 개의 작은 Service로 나뉘어 있고, 이 Service들은 서로 독립적으로 배포되고 스케일링됩니다. 또한 원본 ParksMap 애플리케이션 모음은 **폴리글랏(polyglot)** 하게 설계되어 있어, 각 Service를 Java, .NET, Node.js 등 서로 다른 언어와 프레임워크로 구현할 수 있습니다. 다만 이 워크숍에서는 혼란을 줄이기 위해 모든 Service를 **Java**로 통일해서 진행합니다.

== 메인 Service: 프런트엔드 지도 애플리케이션

메인 Service는 사용자가 브라우저로 접속하는 웹 애플리케이션으로, 두 가지 핵심 구성 요소로 이루어져 있습니다:

1. **서버 측 구성 요소**: 여러 독립적인 백엔드 Service가 제공하는 지리공간 API를 대신 찾아서 호출하고, 그 결과를 모아서(집계) 클라이언트에 전달합니다. 브라우저가 각 백엔드의 주소를 일일이 알 필요가 없도록, 이 서버 측 구성 요소가 일종의 게이트웨이 역할을 하는 것입니다.
2. **클라이언트 측 구성 요소**: JavaScript로 구축되며, 지도에 지리공간 데이터를 시각화하고 WebSocket을 사용하여 서버 측과 통신해 지도를 실시간으로 업데이트합니다. 즉, 새 백엔드가 추가되면 페이지를 새로고침하지 않아도 지도에 자동으로 반영됩니다.

== 백엔드 Service: 실제 지도 데이터를 제공하는 곳

원본 ParksMap 애플리케이션 모음에는 다양한 지도 및 지리공간 정보를 제공하는 독립적인 백엔드 Service들이 있습니다:

* 전 세계 국립공원(National Parks) 정보를 제공하는 **nationalparks** Service
* 북미 메이저리그 야구 경기장(MLB Stadiums) 정보를 제공하는 **mlbparks** Service

이 워크숍에서는 이 중 **nationalparks** 하나만 직접 배포하고 실습합니다. mlbparks는 원본 애플리케이션 모음에 존재하는 백엔드이지만, 이번 워크숍의 실습 범위에는 포함되지 않습니다.

== 백엔드는 어떻게 서로를 찾을까요?

ParksMap 웹 애플리케이션의 서버 측 구성 요소는 사용 가능한 모든 백엔드에 대한 통신 게이트웨이 역할을 합니다. 이때 어떤 백엔드가 존재하는지는 소스 코드에 하드코딩되어 있지 않습니다. 대신 OpenShift가 제공하는 서비스 디스커버리(service discovery) 메커니즘을 사용해, 특정 Label이 붙은 Route를 클러스터에서 동적으로 검색합니다. 즉 nationalparks Service에 올바른 Label을 붙이는 순간, ParksMap이 이를 자동으로 발견해서 지도에 표시해 줍니다. 이 Label을 실제로 붙이는 방법은 뒤에 나올 실습에서 직접 다룹니다.
