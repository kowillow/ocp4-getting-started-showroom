= 권한
:navtitle: 권한

include::vars.adoc[]

OpenShift 환경에서 생각할 수 있는 거의 모든 상호작용은
OpenShift의 Control Plane API를 거쳐야 합니다. 모든 API 상호작용은 인증(AuthN - 당신은 누구인가?)과
인가(AuthZ - 요청한 작업을 수행할 권한이 있는가?)를 모두 거칩니다.

로깅 섹션에서 **Service Account**와 관련된 오류를 확인했습니다.

OpenShift는 선언적 플랫폼이므로, 일부 작업은 최종 사용자가 명령을 실행하는 것이 아니라 플랫폼 자체에 의해 수행됩니다. 이러한 작업은 플랫폼이 내부적으로 사용하는 특수한 유형의 ``user``인 **Service Account**를 통해 수행됩니다.

OpenShift는 모든 project에 몇 가지 특수한 service account를 자동으로 생성합니다.
**default** service account는 Pod를 실행하는 역할을 담당하며, OpenShift는 실행되는
모든 Pod에 이 service account를 자동으로 주입합니다. 이 service
account의 권한을 변경하면 추가 기능을 활성화할 수 있습니다.

웹 콘솔에서 현재 권한을 확인하려면 **OCP Console** 탭의 **Topology** 화면으로 이동하여 ``parksmap`` 항목을 클릭하고, **Details** 탭으로 이동한 후 **Namespace**를 클릭합니다.

[.bordershadow]
image::parksmap-permissions-namespace.png[parksmap Details 탭에 표시된 Namespace 링크 화면,link="self",window=_blank]

**Role Bindings** 탭을 선택하고 **Namespace Role Binding**으로 필터링하면 선택한 project에 대한 모든 권한을 확인할 수 있습니다.

[.bordershadow]
image::parksmap-permissions-membership.png[Namespace Role Binding으로 필터링한 Role Bindings 목록,link="self",window=_blank]

[#grant_serviceaccount_view_permissions]
== Service Account에 View 권한 부여하기
parksmap 애플리케이션은 OpenShift API와 통신하여 여러분의 **Project** 내에 있는 다른
**Pod**, **Service**, 리소스에 대한 정보를 알아내려고 합니다. 그 이유는 곧 알게 됩니다!

parksmap 애플리케이션은 클러스터에서 여러분의 project 내 **Service Account**로 실행됩니다. 구체적으로는 ``default`` **Service Account**입니다. 이 **Service Account**에 필요한 ``view`` 접근 권한을 부여하면 API를 조회하여 **Project** 내에 어떤 리소스가 있는지 확인할 수 있게 됩니다. 이렇게 하면 앞서 로그에서 보았던 오류 메시지의 원인이 해결됩니다.

아래 옵션 중 하나를 선택하여 - **OpenShift 콘솔** 또는 **``oc`` 명령줄** - ``{ocp4_starter_project}`` project의 ``default`` **Service Account**를 업데이트하세요:

====
**옵션 A: OpenShift 콘솔:**

. **Home** -> **Projects** -> **{ocp4_starter_project}**로 이동한 후 **Role Bindings**로 이동하여 **Create Binding** 버튼을 클릭합니다.
+
image::parksmap-permissions-membership-serviceaccount-list.png[Role Bindings 페이지에서 Create Binding 버튼을 클릭하는 화면,link="self",window=_blank]
+
. 다음 필드를 구성합니다:
  * Role Binding Name: **view**
  * Namespace: **{ocp4_starter_project}**
  * Role Name: **view**, Subject: **Service Account**
  * Subject Namespace: **{ocp4_starter_project}**
  * Subject Name: **default**.
+
image::parksmap-permissions-membership-serviceaccount-edit.png[view Role Binding 생성에 필요한 필드를 입력하는 화면,link="self",window=_blank]
+
. 권한 편집이 끝나면 **Create** 버튼을 클릭합니다. 그러면 ``{ocp4_starter_project}`` project의 **RoleBindings** 목록에서 새로 생긴 ``view`` 항목을 확인할 수 있습니다.
+
image::parksmap-permissions-membership-serviceaccount-done.png[생성 완료 후 RoleBindings 목록에 표시된 view 항목,link="self",window=_blank]

**옵션 B: ``oc`` 명령줄:**

먼저 올바른 project 컨텍스트에 있는지 확인합니다:

[source,bash,role="copypaste",subs="attributes"]
----
oc project {ocp4_starter_project}
----

그런 다음 ``oc policy add-role-to-user`` 명령을 사용하여 미리 정의된 ``view`` role을 service account에 부여합니다:

[source,bash,role="copypaste"]
----
oc policy add-role-to-user view -z default
----

.``-z`` 플래그는 무엇을 하나요?
****
``oc policy``의 ``-h`` 출력에 따르면:

[source]
----
-z, --serviceaccount=[]: service account in the current namespace to use as a user
----

``-z`` 구문은 이 경우 전체 문자열인
``system:serviceaccount:{ocp4_starter_project}:default``를 전부 입력하지 않아도 되게 해주는
특별한 표기법입니다. 유용한 단축 방법이죠.
****

NOTE: ``-z`` 플래그는 **현재** project 내의 service account에 대해서만 동작합니다. 다른 project의 service account를 참조하려면 ``-n <project>`` 스위치를 사용하세요.

====

[#redeploy_application]
== 실습: 애플리케이션 재배포하기

``oc rollout`` 명령을 사용하여 ``parksmap`` 애플리케이션을 재시작합니다. 이렇게 하면 새 Pod가 생성됩니다.

[source,bash,role="copypaste"]
----
oc rollout restart deployment/parksmap
----

새로운 배포가 즉시 시작됩니다. Topology 화면으로 돌아가 ``parksmap`` 항목을 다시 클릭하여 그 과정을 지켜보세요. 배포는 빠르게 진행되지만, **ReplicaSet** 번호가 변경되는 것을 확인할 수 있습니다. 또한 ``oc get pods`` 명령을 사용하면 새 Pod의 나이(age)가 불과 몇 초밖에 되지 않은 것을 확인할 수 있습니다.

[.bordershadow]
image::parksmap-permissions-redeployed.png[재배포 후 새로운 ReplicaSet과 Pod가 생성된 Topology 화면,link="self",window=_blank]

애플리케이션 로그를 확인하면 오류가 없어야 합니다.
