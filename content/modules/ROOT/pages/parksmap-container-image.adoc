[#deploy_your_first_image]
== 실습: 첫 번째 컨테이너 이미지 배포하기

가장 간단한 방법부터 시작해 보겠습니다. 평범한 Docker 형식 이미지를 OpenShift에서 실행해 보는 것입니다.
이 작업은 매우 간단하며, OpenShift에서는 웹 콘솔에서 직접 수행할 수 있습니다.

**OCP Console** 탭에서 **{ocp4_starter_project}** Project의 **토폴로지** 화면으로 이동합니다.

왼쪽 상단의 **+** 아이콘을 클릭합니다. OpenShift에 애플리케이션을 배포할 수 있는 여러 옵션이 있는 메뉴가 표시됩니다. 배포하려는 이미지의 정보를 지정할 수 있는 대화 상자를 열려면 **컨테이너 이미지**를 클릭합니다.

[.bordershadow]
image::openshift-console-add-container.png[Container images 배포 옵션을 입력하는 대화 상자,link="self",window=_blank]

'외부 레지스트리의 이미지 이름' 아래에 **Image Name** 필드에 다음을 복사하여 붙여넣습니다:

[source,bash,role="copypaste",subs="attributes"]
----
{ocp4_starter_parksmap_image}
----

그러면 OpenShift가 지정된 컨테이너 레지스트리에 접근하여 이미지 세부 정보를 가져옵니다.

화면은 다음과 같은 모습이 됩니다:

[.bordershadow]
image::parksmap-image.png[이미지 이름 입력 후 표시되는 parksmap 이미지 세부 정보 화면,link="self",window=_blank]

**런타임 아이콘**에서 OpenShift 토폴록지 화면에 표시할 아이콘을 선택합니다. 이 프런트엔드는 Spring Boot로 만들어졌으므로 **spring-boot**를 선택합니다.

다음 값이 설정되어 있는지 확인합니다:

**애플리케이션 이름** :
[source,text,role=copypaste]
----
workshop
----

**이름** :
[source,text,role=copypaste]
----
parksmap
----

NOTE: **애플리케이션 이름**은 전체 애플리케이션의 이름이며, **이름** 필드는 개별 구성 요소에 부여된 이름을 나타냅니다. 이 경우 ``parksmap`` 구성 요소가 배포할 컨테이너입니다.

**리소스 유형** 섹션에서 **배포(Deployment)**가 선택되어 있는지 확인합니다.

NOTE: **리소스 유형**에 대해서는 이후 챕터에서 자세히 다룹니다.

**"고급 옵션"** 아래에 있는 **경로 생성(Create a route)** 옆의 체크박스를 **해제**합니다. 학습을 위해 이 워크숍의 나중 단계에서 애플리케이션용 **경로(Route)**를 직접 생성해 볼 것입니다.

페이지 하단의 '이름을 클릭하여 고급 옵션에 액세스합니다' 부분에서 **라벨(Labels)**를 클릭하고, 나중에 이 배포(Deployment)를 식별하는 데 사용할 수 있는 레이블을 추가합니다. 레이블은 웹 콘솔과 명령줄에서 구성 요소를 식별하고 필터링하는 데 도움이 됩니다.

레이블 3개를 추가합니다. 각 레이블에 대해 name=value 쌍을 입력한 후 다음 레이블을 입력하기 전에 kbd:[Return] 키(키보드에 따라 kbd:[Enter] 키)를 누릅니다. 첫 번째 레이블은 전체 애플리케이션의 이름입니다.

[source,text,role=copypaste]
----
app=workshop
----

다음은 이 배포(Deployment)의 이름입니다.

[source,text,role=copypaste]
----
component=parksmap
----

마지막으로, 이 구성 요소가 전체 애플리케이션에서 수행하는 역할입니다.

[source,text,role=copypaste]
----
role=frontend
----

[.bordershadow]
image::parksmap-image-options.png[Runtime Icon과 이름 및 레이블을 설정하는 이미지 배포 옵션 화면,width=600,link="self",window=_blank]

[.bordershadow]
image::parksmap-advanced-image-options.png[Create a route 체크 해제 등 고급 옵션과 레이블 입력 화면,width=600,link="self",window=_blank]

이제 파란색 **만들기(Create)** 버튼을 클릭합니다. **토폴로지** 페이지로 이동하며, ``workshop`` 애플리케이션 내 ``parksmap`` 배포에 대한 시각화를 확인할 수 있습니다.

[.bordershadow]
image::parksmap-dc-topology.png[Topology 화면에 표시된 workshop 애플리케이션의 parksmap 배포 아이콘,width=400,link="self",window=_blank]

OpenShift에서 컨테이너 이미지를 배포하는 데 필요한 단계는 이것이 전부입니다. EXPOSE 포트를 정의하는 것, **root 사용자**나 다른 사용자 이름으로 실행할 필요가 없는 것, 시작 시 실행할 종료되지 않는 단일 CMD를 갖는 것과 같은 모범 사례를 따르는 모든 컨테이너 이미지에서 이 방식이 동작합니다. 이러한 내용은 이 애플리케이션의 https://github.com/openshift-roadshow/parksmap-web/blob/master/Dockerfile[Dockerfile^]에서 확인할 수 있습니다.

NOTE: 애플리케이션을 대규모로 배포할 때는 적절한 레이블을 지정하는 것이 중요합니다. OpenShift는 Overview 페이지에서 구성 요소를 정의하고 그룹화하기 위해 **app** 레이블을 사용합니다. 명시적으로 지정하지 않으면 OpenShift가 기본값으로 이 레이블을 생성합니다.

[#containers_and_pods]
== 배경 지식: 컨테이너와 Pod

본격적으로 시작하기 전에, 컨테이너와 **Pod**가 어떻게 연관되어 있는지 이해하는 것이 중요합니다. 이 워크숍에서는 이러한 기술의 배경 지식을 자세히 다루지 않지만, 궁금한 점이 있다면 진행자에게 문의해 주세요. 대신 바로 실습을 통해 사용해 보겠습니다.

OpenShift(및 Kubernetes)에서 배포 가능한 가장 작은 단위는 **Pod**입니다. **Pod**는 함께 배포되고 동일한 호스트에서 실행되는 것이 보장되는 하나 이상의 https://opencontainers.org/[OCI 컨테이너^] 그룹입니다.
OpenShift 공식 문서에 따르면 다음과 같습니다:

[quote]
__
각 **Pod**는 고유한 IP 주소를 가지므로 전체 포트 공간을 독점적으로 사용하며, Pod 내의
컨테이너들은 스토리지를 공유할 수 있습니다. **Pod**는 하나 이상의 레이블로 "태그"될
수 있으며, 이 레이블은 한 번의 작업으로 **Pod** 그룹을 선택하고 관리하는 데
사용됩니다.
__

**Pod**는 여러 개의 OCI 컨테이너를 포함할 수 있습니다. 일반적인 개념은 **Pod**가
"메인 프로세스"와 그 프로세스와 함께 실행하고자 하는 보조 서비스들을 포함하는 것입니다. **Pod**에 넣을 수 있는 컨테이너의 예로는 Apache HTTPD
서버, 로그 분석기, 업로드된 파일을 관리하는 파일 서비스 등이 있습니다.

[#customizing_image_lifecycle_behavior]
== 배경 지식: 이미지 라이프사이클 동작 커스터마이징하기

OpenShift가 노드의 CRI(Container Runtime Interface) 런타임(Docker 데몬 또는 CRI-O)에 이미지를 실행하도록 요청할 때마다, 런타임은 실행할 올바른 버전의 이미지를 가지고 있는지 확인합니다.
가지고 있지 않다면 지정된 레지스트리에서 이미지를 pull합니다.

이 동작을 커스터마이징하는 방법은 여러 가지가 있으며, link:{ocp4_starter_openshift_docs}/html/images/managing-images[OpenShift 공식 문서^]에 정리되어 있습니다.

[#services]
== 배경 지식: Service

*Service*는 OpenShift 내부에서 트래픽을 *Pod*로 라우팅하는 편리한 추상화 계층을 제공합니다.
또한 해당 *Pod*로 전송되는 트래픽에 대한 로드 밸런서 역할도 합니다. 예를 들어
증가하는 트래픽을 처리하기 위해 더 많은 `parksmap` 인스턴스가 필요하다면,
*Pod*를 더 늘릴 수 있습니다. OpenShift는 이러한 Pod들을 자동으로
*Service*의 엔드포인트로 매핑하며, 들어오는 요청 입장에서는 `parksmap`이 요청을
더 잘 처리하게 되었다는 것 외에는 별다른 차이를 느끼지 못합니다.

OpenShift에 이미지를 실행하도록 요청했을 때, OpenShift는 자동으로 *Service*를
생성해 주었습니다. Service는 내부적인 구성 요소라는 점을 기억하세요. "외부
세계"나 OpenShift 환경 바깥에 있는 것들은 Service에 접근할 수 없습니다. 괜찮습니다 - 이 문제를 해결하기 위해 나중에 *Route*를 사용하는 방법을 배우게 됩니다.


*Service*는 *Selector*를 사용하여 여러 *Pod*와 매핑됩니다. *Selector*는 *Labels*를 사용하여 어떤 Pod가 트래픽을 받아야 하는지 결정합니다.

직접 YAML 형식으로 작성하는 방법을 포함하여
link:{ocp4_starter_openshift_docs}/html/networking_overview[Service^]에 대한 더 많은 정보는, OpenShift 공식 문서에서 확인할 수 있습니다.

이제 *Service*가 무엇인지 기본 개념을 이해했으니, 방금 배포한 이미지에 대해 생성된
*Service*를 살펴보겠습니다. 여러분의 *Project*에 정의된 *Service*를 확인하려면 다음 명령을 입력합니다:

[source,bash,role="copypaste"]
----
oc get services
----

다음과 유사한 출력이 표시됩니다:

[.console-output]
[source]
----
NAME       TYPE        CLUSTER-IP       EXTERNAL-IP   PORT(S)    AGE
parksmap   ClusterIP   172.31.106.159   <none>        8080/TCP   15m
----

위 출력에서, `parksmap`이라는 이름의 *Service*가
172.30.22.209/8080TCP라는 IP/포트 조합을 가지고 있는 것을 확인할 수 있습니다. 각
*Service*는 생성 시 고유한 IP 주소를 받기 때문에 여러분의 IP 주소는 다를 수 있습니다. *Service*의
IP는 고정되며 해당 *Service*가 존재하는 동안 절대 변경되지 않습니다.

*Topology* 화면에서는 `parksmap` Deployment를 클릭한 후 *Resources*를 클릭하면 Service 정보를 확인할 수 있습니다.

[.bordershadow]
image::parksmap-serviceslist.png[Resources 탭에서 확인한 parksmap Service 연결 정보,link="self",window=_blank]

다음 명령을 사용하여 YAML 형식으로 데이터를 표시함으로써
*Service*에 대한 더 자세한 정보를 확인할 수도 있습니다:

[source,bash,role="copypaste"]
----
oc get service parksmap -o yaml
----

다음과 유사한 출력이 표시됩니다:

[.console-output]
[source]
----
apiVersion: v1
kind: Service
metadata:
  annotations:
    openshift.io/generated-by: OpenShiftWebConsole
  creationTimestamp: "2020-09-30T14:10:12Z"
  labels:
    app: workshop
    app.kubernetes.io/component: parksmap

`parksmap` *Pod*의 YAML을 확인하여 *Service*
가 *Selector*를 어떻게 사용하는지 이해해 보세요. 다음 명령을 실행하여 Pod 정보를 확인합니다:

[source,bash,role="copypaste"]
----
oc describe pods
----

`Labels` 섹션 아래에서 다음을 확인할 수 있습니다:

[.console-output]
[source]
----
app=parksmap
deployment=parksmap
----

이 *Pod* 레이블은 *Service*의 *Selector*가 대상으로 하는 레이블과 일치합니다.

NOTE: *Labels*는 단순한 key-value 쌍입니다. 동일한 *Project*(*Namespace*라고도 함) 내에서 *Selector*와
일치하는 레이블을 가진 모든 *Pod*는 해당 *Service*와 연결됩니다. 이를 직접 확인하려면 다음
명령을 실행하세요:

[source,bash,role="copypaste"]
----
oc describe service parksmap
----
