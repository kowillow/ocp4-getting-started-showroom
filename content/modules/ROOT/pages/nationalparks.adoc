= Nationalparks 백엔드 애플리케이션
:navtitle: Nationalparks 백엔드 애플리케이션

include::vars.adoc[]

이 섹션에서는 시각화 애플리케이션(이전 워크숍 섹션에서 배포한 `parksmap` 웹 구성 요소)에
두 가지 주요 REST 엔드포인트를 노출하는 백엔드 Service를 배포합니다.
이 애플리케이션은 MongoDB 데이터베이스에 저장된 각 국립공원의 정보(좌표 포함)를
조회합니다. 또한 이 애플리케이션은 API를 최종 사용자가 직접 사용할 수 있도록
외부 접근 지점도 제공합니다.

[#source_to_image]
== 배경 지식: Source-to-Image (S2I)

이전 워크숍 섹션에서는 기존에 존재하는 컨테이너 이미지를 배포하는 방법을 배웠습니다.
이번에는 기존 Git 저장소의 소스 코드로부터 OpenShift가 직접 컨테이너 이미지를 빌드하는 방법을 배웁니다. 이는 Source-to-Image 프로젝트를 통해 이루어집니다.

link:{ocp4_starter_openshift_github}/source-to-image[Source-to-Image (S2I),window='_blank']는
Red Hat이 후원하는 오픈소스 프로젝트로, 다음과 같은 목표를 가지고 있습니다:

[quote]
--
Source-to-image(S2I)는 재현 가능한 컨테이너 이미지를 빌드하기 위한 도구입니다. S2I는
소스 코드를 컨테이너 이미지에 주입하고 빌더 이미지와 빌드된 소스를 결합한 새로운
컨테이너 이미지를 조합하여 즉시 실행 가능한 이미지를 만들어냅니다. 그 결과물은 docker run으로
바로 사용할 준비가 됩니다. S2I는 이전에 다운로드한 종속성이나 이전에 빌드된
아티팩트 등을 재사용하는 증분 빌드(incremental build)를 지원합니다.
--

OpenShift는 Dockerfile의 지시어를 사용한 이미지 빌드나 "custom" 빌드 외에도, S2I를 빌드 메커니즘 중 하나로 사용할 수 있습니다.

OpenShift는 S2I 프로세스를 Build Pod라고 하는 특별한 *Pod* 내부에서
실행하므로, 빌드 역시 쿼터, 제한, 리소스 스케줄링 등 OpenShift의
다른 요소들과 마찬가지로 이러한 제약을 받습니다.

S2I에 대한 전체적인 논의는 이 워크숍의 범위를 벗어나지만, 더 자세한 내용은
link:{ocp4_starter_openshift_docs}/html/images/creating-images[OpenShift S2I 문서,window='_blank']나
link:{ocp4_starter_openshift_github}/source-to-image[GitHub,window='_blank']에서 확인할 수 있습니다. S2I에 대해 기억해야 할 유일한
핵심 개념은, 이것이 마법 같다는 것입니다.

[#creating_a_application]
== 실습: 백엔드 애플리케이션 생성하기

이 실습에서 배포할 백엔드 Service는 `nationalparks`라고 합니다. 이 애플리케이션은
MongoDB 데이터베이스에 대해 2D 지리공간 쿼리를 수행하여 전 세계 국립공원의 지도
좌표를 찾아 반환합니다. 조금 어렵게 표현했지만, 결국 장소 목록을 JSON으로
반환하는 웹 서비스를 배포한다는 뜻입니다.

[#add_to_project]
=== Project에 추가하기
`nationalparks` 구성 요소는 기존 프런트엔드(parksmap)가 사용할 데이터를 제공하는
백엔드이기 때문에, 지금까지 사용해 온 기존 project 안에 빌드하고 배포하게 됩니다.

[#using_application_code_on_git_server]
=== Git 서버에서 애플리케이션 코드 사용하기

OpenShift는 접근 가능한 모든 Git 저장소와 함께 동작할 수 있습니다. GitHub,
GitLab, 또는 Git 프로토콜을 지원하는 다른 어떤 서버든 사용할 수 있습니다. 심지어
Git 서버에 webhook을 등록하여 애플리케이션 코드가 업데이트될 때마다 OpenShift 빌드가
시작되도록 할 수도 있습니다!

워크숍 후반부에서는 코드를 변경한 후 애플리케이션을 다시 빌드해 볼 것입니다. 지금은
백엔드 Service를 배포하는 방법을 살펴보겠습니다.

[#deploying_the_backend_service]
=== 백엔드 Service 배포하기

이전에 기존 이미지를 사용할 때 *+* 버튼을 사용했던 것처럼, 소스 코드
저장소를 지정할 때도 동일하게 할 수 있습니다.
간단한 link:{ocp4_starter_openshift_roadshow}/nationalparks.git[Java,window='_blank'] S2I 이미지를 사용해 봅시다.

Topology 화면에서 헤더의 *+* 버튼을 클릭하고 *Import from Git*을 선택합니다.

[.bordershadow]
image::nationalparks-show-add-options.png[link="self",window=_blank]

*Import from Git* 워크플로우는 몇 가지 선택 사항을 통해 앱 배포 과정을 안내해 줍니다.

Git Repo URL에 다음을 입력합니다:

[source,role=copypaste,subs="attributes"]
----
{ocp4_starter_openshift_roadshow}/nationalparks.git
----

OpenShift가 소스 코드에서 사용된 프로그래밍 언어를 자동으로 감지합니다. *Import Strategy*를 선택할 수 있는 옵션이 있습니다.

*Edit Import Strategy*를 클릭합니다.

[.bordershadow]
image::nationalparks-import-strategy.png[width=500,link="self",window=_blank]

세 가지 옵션이 있습니다:

* *Devfile*: link:{ocp4_starter_devfile_docs}[devfile,window='_blank'] 스펙을 사용하여 애플리케이션 스택을 생성합니다. 저장소에는 devfile 형식의 `devfile.yaml` 파일이 있어야 합니다.
* *Dockerfile*: 소스 Git 저장소에 있는 기존 Dockerfile로 컨테이너 이미지를 생성합니다.
* *Builder Image*: Source-to-Image라는 메커니즘을 사용하여 소스 코드로부터 직접 컨테이너 이미지를 자동으로 생성합니다 - Dockerfile이 필요하지 않습니다.

다음 섹션에서 다룰 내용처럼 소스 코드로부터 컨테이너 이미지를 생성할 것이므로 *Builder Image*를 선택합니다.

[.bordershadow]
image::nationalparks-import-strategy-build.png[link="self",window=_blank]

TIP: 저장소에는 멀티 스테이지 Dockerfile도 포함되어 있으므로 Dockerfile을 사용할 수도 있습니다. 이 실습의 목표는 OpenShift의 Builder Image 기능을 경험해 보는 것입니다.

Builder Image로 *Java*가 선택되었는지 확인하고, OpenJDK 11을 사용하도록 버전 *openjdk-11-ubi8*이 선택되어 있는지 확인하세요.

아래로 스크롤하여 *General* 섹션으로 이동합니다. 다음을 추가합니다:

*Application Name* :
[source,role=copypaste]
----
workshop
----

*Name* :
[source,role=copypaste]
----
nationalparks
----

*Build* 섹션에서 *BuildConfig*를 선택합니다.

*Deploy* 섹션에서 *Deployment*를 선택합니다.

*Advanced Options* 아래에서 *Create a route*가 *체크*되어 있는지 확인합니다. 이번에는 이 화면에서 직접 또 다른 *Secure Route*를 생성하게 됩니다.

*Show advanced Routing options*를 클릭합니다. 기본 옵션은 그대로 두고 *Security* 섹션으로 이동합니다. *Secure Route* 옵션을 체크합니다. *TLS termination* 아래에서 *Edge*를 선택합니다.

[.bordershadow]
image::nationalparks-configure-service1.png[link="self",window=_blank]

[.bordershadow]
image::nationalparks-configure-service2.png[link="self",window=_blank]

아래로 스크롤하여 *Labels* 섹션을 펼쳐 레이블 3개를 추가합니다.

[.bordershadow]
image::nationalparks-configure-service4.png[link="self",window=_blank]

[.bordershadow]
image::nationalparks-configure-service3.png[link="self",window=_blank]

Application 그룹의 이름입니다:

[source,role=copypaste]
----
app=workshop
----

다음은 이 배포의 이름입니다:

[source,role=copypaste]
----
component=nationalparks
----

마지막으로, 이 구성 요소가 전체 애플리케이션에서 수행하는 역할입니다:

[source,role=copypaste]
----
role=backend
----

*Create*를 클릭하여 제출합니다.

[#monitoring-the-build]
=== 빌드 모니터링하기

빌드 로그를 확인하려면 Topology 화면에서 `nationalparks` 항목을 클릭한 후, *Resources* 탭의 *Builds* 섹션에서 *View Logs*를 클릭합니다.

[.bordershadow]
image::nationalparks-java-new-java-build.png[link="self",window=_blank]

애플리케이션의 언어에 따라 빌드 프로세스는 다르게 진행됩니다. 다만 종속성을 다운로드하는 초기 빌드는 몇 분 정도 걸립니다. 이 모든 과정을 실시간으로 확인할 수 있습니다!

명령줄에서도 *Build*를 확인할 수 있습니다:

[.console-input]
[source,role="copypaste"]
----
oc get builds
----

다음과 같은 출력이 표시됩니다:

[.console-output]
[source]
----
NAME              TYPE      FROM          STATUS     STARTED              DURATION
nationalparks-1   Source    Git@b052ae6   Running    About a minute ago   1m2s
----

다음 명령으로 빌드 로그를 확인할 수도 있습니다:

[.console-input]
[source,role="copypaste"]
----
oc logs -f builds/nationalparks-1
----

빌드가 성공적으로 완료되면:

* S2I 프로세스가 결과 이미지를 내부 OpenShift 이미지 레지스트리에 푸시합니다
* *Deployment*(D)가 이미지가 변경된 것을 감지하고, 이로 인해
  새로운 배포가 발생합니다.
* 이 새 배포를 위한 *ReplicaSet*(RS)이 생성됩니다.
* 기본 레플리카 개수가 1이므로, RS는 실행 중인 *Pod*가 없음을 감지하고 하나를 배포합니다.

결국 `oc get pods` 명령을 실행하면, 빌드 Pod는
완료(종료)되었고 애플리케이션 *Pod*는 준비되어 실행 중인 상태인 것을 확인할 수 있습니다:

[.console-output]
[source]
----
NAME                        READY     STATUS      RESTARTS   AGE
nationalparks-1-tkid3       1/1       Running     3          2m
nationalparks-1-build       0/1       Completed   0          3m
parksmap-57df75c46d-xltcs   1/1       Running     0          2h
----

다시 OpenShift 웹 콘솔을 살펴보세요. 애플리케이션을 생성할 때 활성화했기 때문에 *Route*가 생성된 것을 확인할 수 있습니다. 웹 콘솔에서 URL을 확인하거나 명령줄에서 확인할 수 있습니다:

[.console-input]
[source,role="copypaste"]
----
oc get routes
----

다음과 유사한 결과가 표시됩니다:

[.console-output]
[source,role="copypaste",subs="attributes"]
----
NAME            HOST/PORT                                                   PATH      SERVICES        PORT       TERMINATION       WILDCARD
nationalparks   nationalparks-{ocp4_starter_project}.{ocp4_starter_apps_domain}      nationalparks   8080-tcp        edge
parksmap        parksmap-{ocp4_starter_project}.{ocp4_starter_apps_domain}           parksmap        8080-tcp        edge        none
----

위 예시에서 URL은 다음과 같습니다:

[.console-output]
[source,subs="+attributes"]
----
https://nationalparks-{ocp4_starter_project}.{ocp4_starter_apps_domain}
----

이는 백엔드 애플리케이션이므로 실제 웹 인터페이스는 없습니다.
그러나 브라우저로도 사용해 볼 수 있습니다. parksmap 프런트엔드와 함께 동작하는 모든 백엔드는
`/ws/info/` 엔드포인트를 구현해야 합니다. 테스트하려면 브라우저에서 다음 URL을 방문하세요:

link:https://nationalparks-{ocp4_starter_project}.{ocp4_starter_apps_domain}/ws/info/[National Parks Info Page,window='_blank']

WARNING: Pod가 Running 상태인데도 애플리케이션이 사용 불가능하다면, 아직 Health Check를 구성하지 않았기 때문이니 몇 초 기다렸다가 페이지를 새로고침해 보세요.

간단한 JSON 문자열이 표시됩니다:

[source]
----
{"id":"nationalparks","displayName":"National Parks","center":{"latitude":"47.039304","longitude":"14.505178"},"zoom":4}
----

워크숍 앞부분에서 다음 내용을 읽었습니다:

_이 애플리케이션은 MongoDB 데이터베이스에 대해 2D 지리공간 쿼리를 수행합니다_

하지만 아직 데이터베이스가 없습니다. 아직은요.
